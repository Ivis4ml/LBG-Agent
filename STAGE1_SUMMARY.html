§ 1

The architecture, as built

The Orchestrator is a deterministic Python control plane. It schedules every LLM call, applies every edit, runs every invariant, and writes every artifact. The Orchestrator itself contains no LLM call — its determinism is the credibility of the experiment. Three LLM roles sit at the leaves; everything else is plain Python.

Figure 1. The 13 deterministic submodules surround the three LLM-driven roles in the middle. Yellow dashed lines are the structural redaction layer: agents never receive raw OHLCV, calendar years, or validation numbers. Stage 2 and Stage 3 reuse the same backtest engine with no LLM.

The thirteen submodules, briefly

RoleRunnerProvider-agnostic LLM wrapper. Reads LBG_PROVIDER; speaks the Anthropic SDK against either api.anthropic.com or MIMO's anthropic-compatible endpoint. Two-way redaction guards every call.

Three LLM roles, two providers

The three LLM-driven roles share a single RoleRunner with a provider registry:

lbg/orchestrator/role_runner.py · PROVIDERS 
PROVIDERS = {
  "anthropic": ProviderConfig(
    api_key_env="ANTHROPIC_API_KEY",

    default_model="claude-opus-4-7"),

The Anthropic SDK is the only client library; MIMO is invoked via its anthropic-compatible REST endpoint with a different base_url. Switching providers is one flag: RoleRunner(provider="mimo") or environment LBG_PROVIDER=mimo. The rest of the Orchestrator never knows which model answered.

Why a provider abstraction matters here The H1 verdict, the per-trial gate, the invariant suite — none of these depend on which LLM generated the proposal. Validating that we get the same sealed metrics regardless of provider (we do, to the last decimal) is a proof that the Orchestrator's determinism claim survives provider swaps. See §7 for the cross-provider sanity check.
§ 2

The Discovery loop, in motion

One trial is one budget step. Each step proposes, builds, gates, reflects, and commits — or aborts cleanly and moves on. The loop is small enough to write out:

Algorithm 1 · one trial 
for i in range(budget):
  trial_id = start_id + i                              # sequential, even on abort
  ctx       = ContextBuilder.editor_view(incumbent)
  proposal  = RoleRunner.editor(ctx, trial_id)         # LLM call #1
  candidate = CandidateBuilder.apply(incumbent, proposal)

  if InvariantRunner.fail(candidate, df_train):       # AST + prefix_stability + sandbox
    MemoryManager.append_invariant_failure(...); continue

  train  = BacktestRunner.run(candidate, df_train)
  val    = BacktestRunner.run(candidate, df_val)

  gate   = ValidationGate.decide(incumbent_outcome, candidate_outcome)
  signal = ValidationGate.redact(gate)                 # one of 5 categorical values
  outcome = HypothesisScorer.compare(proposal, signal, train.sharpe_delta)

  refl   = RoleRunner.reflector(ctx, proposal,         # LLM call #2
                                outcome, signal, train.metrics)

  MemoryManager.append_trial(record)                   # trials.jsonl
  MemoryManager.append_reflection(refl.record)         # reflections.jsonl
  MemoryManager.append_to_md(refl.record.updates)      # 4 semantic md files
  GitManager.commit_trial(trial_id, edit_summary)

  if gate.accepted:
    incumbent, incumbent_outcome = candidate, candidate_outcome
  else:
    restore_working_tree(incumbent)

  if Curator.should_run(accepted_count):                # every 10 accepted
    Curator.run(cycle=...)                             # LLM call #3, shadow mode

# end of loop
sealed_metrics = BacktestRunner.run(incumbent, df_sealed)
h1_verdict     = compute_h1_verdict(sealed.returns, df_sealed)
SealedVault.open_and_write({..., h1_verdict})         # write-once
ReportBuilder.build()                                  # final HTML

Two LLM calls per trial (Editor + Reflector). A third LLM call fires per Curator cycle, every 10 accepted trials. In a 20-trial run with 0 accepted, the loop costs 40 LLM calls.

§ 3

Layered defenses against agent code

An LLM that can author Python and influences a backtest is, on day one, an adversary against the metrics — through accident, not malice. The invariant stack is what keeps it from reward-hacking its way to a fake Sharpe.

shift(-1), bfill, import os, print/open/eval in indicator code. 3 · SandboxExecutor stripped builtins · SIGALRM timeout Runtime __import__ hook + 42 safe builtins. import os in a function body still raises. 4 · prefix_stability (dynamic) ∀ t : f(D)[t] == f(D[:t+1])[t] Perturbs D_>t; catches whole-series normalisation, global percentile, hidden lookahead. 5 · Gate-side runtime checks cost_model_required · max_position · sandbox_execution Backtest with zero cost on non-zero turnover ⇒ rejected. No implicit leverage. Each layer is strict enough that the layer below it is defense in depth, not duplication.
Figure 3. Five layers between an LLM-generated indicator and a backtest. AST static catches what the agent writes; the sandbox catches what survives static analysis at runtime; prefix_stability catches the semantically subtle leaks the AST can never see. In our 20-trial Anthropic run, 12 of 20 trials were stopped by one of these layers before reaching the gate.

The single most load-bearing check

Of the five layers, prefix_stability is the one that justifies the others' existence. The formal statement, from PROPOSAL §4.5:

\[ f\!\left(D_{1:T}\right)\!\bigl[t\bigr] \;=\; f\!\left(D_{1:t}\right)\!\bigl[t\bigr] \qquad \forall\, t \in \{1, \ldots, T\} \] For any indicator f, its value at time t when applied to the full series must equal its value at t when applied to the prefix ending at t. Stricter than scanning the AST for shift(-1); catches normalisation, percentile, every channel through which D>t could enter f(D)[t].

Operationalised: sample 30 random ts, replace df.iloc[t+1:] with a randomised OHLCV block (every row scaled by U(0.5, 1.5), OHL co-scaled to preserve high≥close≥low), recompute the indicator, and compare the head [0..t] to the unperturbed baseline. Any difference greater than atol=1e-12 is a leak. Two leaky LLM-authored indicators we caught in the wild:

IndicatorWhy it leaks
whole_series_zscore (s - s.mean()) / s.std(). The mean and std at t=500 depend on every future row. AST can't see this — no shift, no iloc, no fill. prefix_stability catches it on the first perturbation: every value at t≤500 changes when D>500 changes.
normalize_to_global_max close / close.max(). Identical structural issue, even simpler. First differing index after perturbation: 0.

Both were generated by the LLM Editor unprompted during dry runs of the framework. Both were rejected before any backtest. That is the layer working.

An honest limit prefix_stability sampling cannot prove no-lookahead — it can only refute it. With n_samples=30, a leak that happens at one particular t in 3000 will pass roughly 99% of the time. Production runs sample more aggressively and the Curator records every false-pass as evidence to widen the sample. The current default is enough for daily-bar indicators in our DSL but is not a substitute for a formal proof.
§ 4

The validation gate

The per-trial gate is the part of the system most likely to silently misalign with the H1 verdict if you're not careful. It is not the H1 verdict. It is intentionally looser so the Discovery loop does not starve, but strict enough that fluke accepts on a thin validation window don't poison the search.

lbg/gate/decision.py · decide() 
def decide(incumbent, candidate, cfg):
  if candidate.train.num_trades < cfg.min_trades:        return Reject("too_few_trades")
  if candidate.val.max_drawdown < incumbent.val.max_drawdown * 1.15:
                                                          return Reject("drawdown_regression")
  if candidate.val.turnover > cfg.max_turnover:           return Reject("turnover_too_high")
  if candidate.complexity - incumbent.complexity > cfg.max_delta:
                                                          return Reject("complexity_increase")

  u_cand = utility_lcb_sharpe(candidate.val.returns, α=0.20)
  u_inc  = utility_lcb_sharpe(incumbent.val.returns,  α=0.20)
  if u_cand > u_inc + cfg.eps:                            return Accept("utility_improvement")

  if pareto_dominates(candidate, incumbent, cfg.eps):     return Accept("pareto_improvement")

  if candidate.train.sharpe - candidate.val.sharpe > cfg.max_gap:
                                                          return Reject("overfit_gap")
  return Reject("no_meaningful_improvement")

Why one-sided utility LCB at α = 0.20

The Lo (2002) asymptotic standard error for the sample Sharpe estimator under iid daily returns:

\[ \widehat{\mathrm{SE}}(\hat S) \;\approx\; \sqrt{\frac{1 + \tfrac{1}{2}\hat S^{2}}{n}} \cdot \sqrt{252} \] n = validation-window length (~505 daily bars in split_B). Ŝ = annualised point estimate. The one-sided lower bound at α=0.20 uses z0.80 ≈ 0.842 — looser than 95% CI on purpose so the per-trial gate doesn't reject every honest small improvement on a 500-bar window.

The gate compares candidate LCB to incumbent LCB, not point estimates. A candidate must beat the incumbent's lower-confidence Sharpe by at least EPS = 0.005. Two candidates with identical realised returns score equal LCBs, so the gate falls through to the Pareto check — which can still accept on the basis of complexity, drawdown, or turnover.

The five categorical signals the LLM sees

Behind the gate is rich numeric reasoning. The LLM sees one of five strings:

External signalInternal reasons mapped here
acceptedaccept_utility_improvement, accept_pareto_improvement
rejected_drawdown_regressionval MDD worse than incumbent × 1.15
rejected_turnoverval turnover exceeded cap (default 10/yr)
rejected_complexityΔcomplexity exceeded MAX_DELTA (default 3.0)
rejected_no_significant_improvementtoo_few_trades, overfit_gap, no_meaningful_improvement — the catch-all "didn't move the needle"

The collapse of three internal reasons into rejected_no_significant_improvement is intentional. The LLM should not learn to distinguish "I made too few trades" from "I overfit train" — both mean "your edit did not progress the strategy", and the right response is the same: try a different shape of edit. Distinguishing them in agent context would invite reward hacking on the easier of the two.

Complexity, the full formula

Five terms, all weights locked by §20 lock-list:

\[ \mathrm{Complexity}(H) \;=\; \lambda_1 |A_k| + \lambda_2 |\text{filters}| + \lambda_3 |\text{params}| + \lambda_4 \cdot \mathrm{LOC} + \lambda_5 \cdot \#\text{branches} \] Weights (frozen): λ1=1.0 (indicators), λ2=0.5 (filters), λ3=0.1 (params), λ4=0.005 (effective LOC across all indicator files), λ5=0.05 (If/While/For/Try AST nodes). LOC + branch are summed across distinct indicator files — two specs sharing one fn don't double-count.

An add_indicator that imports a 50-line, 3-branch ATR implementation contributes 1.0 + 0.005·50 + 0.05·3 = 1.4 to complexity. MAX_DELTA = 3.0 means about two such additions in one trial; the third must wait for a Curator simplify pass.

§ 5

The sealed window and the H1 verdict

The single most important architectural invariant is that the agent never sees split_C. Not its data, not its metrics, not the calendar dates of its boundaries. The Orchestrator opens it once at the end of the run, writes the verdict to a write-once vault, and the human reads it.

Figure 4. The three splits are aliased so the LLM cannot infer the calendar. Years on the axis here are for human readers only; the splits arrive at the agent as split_A / split_B / split_C. Vault opens once.

The H1 test in one expression

The final verdict is a moving-block bootstrap confidence interval on the paired difference in sealed Sharpe between LBG-Trader and the strongest pre-registered baseline:

\[ \Delta\hat{S} \;=\; \hat{S}_{\text{LBG}} - \hat{S}_{B^{*}} \quad\text{with}\quad \mathrm{CI}_{95\%}(\Delta\hat{S}) \;=\; \bigl[\hat{q}_{2.5\%},\, \hat{q}_{97.5\%}\bigr] \] q̂ percentiles taken across 1000 bootstrap resamples; each resample draws ⌈n / block_len⌉ overlapping blocks of length 10 from the paired daily-returns series with replacement and recomputes both Sharpes. B* is the stronger of the two pre-registered baselines (buy-and-hold, sixty-forty) by point Sharpe on split_C.

The strong criterion is CI.lower > 0. The weak criterion is ΔŜ > 0. Both criteria are reported; the strong is what the verdict turns on.

Why a block bootstrap

Daily SPY returns have non-negligible autocorrelation, especially in volatility. An iid bootstrap (resample individual days) would erase that structure and inflate the apparent precision of the Sharpe estimate. Moving blocks of length 10 preserve short-horizon autocorrelation while still providing enough independent draws for a stable 95% CI from n=1000.

The file is chmod 0o444'd after writing. Any second call raises SealedVaultError. The vault is the project's single load-bearing claim about generalisation — and it cannot be tampered with via the Orchestrator.

§ 6

Defenses against sycophancy

An LLM Reflector asked "was this trial confirmed?" will tend to answer yes, especially if the system prompt cares about progress. The defense is structural, not exhortatory: we never ask the Reflector that question.

"Memory is what happened. The Reflector explains; the Orchestrator judges."

HypothesisScorer.compare — the mechanical part

The Editor's proposal includes two enumerated predictions:

  • expected_train_signal ∈ {strong_improvement, mild_improvement, neutral, mild_regression, strong_regression}
  • expected_validation_signal ∈ {accept, reject}

After the gate runs, the Orchestrator computes delta_sharpe_train = candidate.train.sharpe − incumbent.train.sharpe and buckets it into the same five categories using fixed thresholds (±0.05, ±0.30). The Reflector is then told the result — not asked for it.

train bucketval matchHypothesisOutcome
matchedmatchedconfirmed
mismatchedmismatcheddisconfirmed
exactly one of the two matchedpartially_confirmed

The Reflector's job is then narrow: given the outcome, explain mechanically what in the strategy's mechanics drove it. The system prompt forbids restating the outcome, forbids judging the hypothesis, and requires bullet-shaped updates to four semantic-memory documents. ReflectorOutputPayload has no hypothesis_outcome field — the schema makes overriding the mechanical result structurally impossible.

Three layers of redaction

L1
Structural. PastTrialSummary has no validation_sharpe / validation_max_drawdown / validation_turnover field. The Editor literally cannot see val metrics because the dataclass that carries trial history does not contain them. Test test_past_trial_summary_omits_validation_metrics asserts this on every CI run.
L2
Textual, outgoing. Every assembled prompt is scanned by assert_redacted before messages.create fires. Patterns: 4-digit years in [1990, 2050], ISO dates, 35 named market events (covid, gfc, lehman, brexit, 9/11, …). A hit raises RedactionError before any token reaches the network.
L3
Textual, incoming. The same scanner runs on the LLM's raw response. If a model hallucinates "after the 2020 drawdown..." into its reflection, we crash hard rather than persist a leaky bullet into accepted_rules.md. The whole trial is aborted; no Editor turn ever sees it.

What the Reflector actually accumulates

Even with zero accepted trials, the Reflector produces real, mechanical, evidence-grounded bullets. From the MIMO run's failed_directions.md:

"Switching to volatility_target sizing alone on a high-frequency SMA-cross strategy without restructuring entry/exit rules causes excessive position resizing and trade proliferation, yielding no net improvement."

"Widening the slow SMA from 50 to 100 (keeping fast at 20) reduces trade count but delays exits enough to worsen Sharpe and cause drawdown regression in validation; the slower crossover is too blunt a filter."

These are unforced, post-hoc explanations of why the gate said no. They name the mechanism (excessive position resizing, blunt filter), not just the symptom. Three trials in, the system already has a non-trivial map of dead ends — and the Editor reads it on the next turn.

The shape of failure

Three patterns survive both runs:

  1. Both providers independently discovered the same best improvement. change_sizing_mode → volatility_target produced train Sharpe 0.722 (a +0.029 lift over baseline) on Anthropic trial 1 and MIMO trial 0 — bit-identical numbers. This is the strongest evidence that the Orchestrator's determinism claim survives provider swaps, and a small confirmation of the LBG idea that good edits are discoverable.
  2. Every real improvement on train made val worse. Vol-target sizing: val Sharpe 0.933 → 0.876. SMA period widening: val Sharpe 0.933 → 0.223. The val window is a regime peculiarly favourable to the baseline; any move costs you. This is exactly what a generalisation-resistant gate must catch.
  3. Acceptance rate = 0 / 24. Not by design — by data. With min_trades=20 and a 1.15× MDD floor on a small val window, the gate is unforgiving, and the LLM's single-step edits cannot solve "this baseline is near a local optimum within its DSL". This is the negative result.

A bug exposed by MIMO The MIMO run revealed that the original loop's trial-id allocation came from max(trials.jsonl) + 1. Aborted trials (parser/redaction failures) don't write to trials.jsonl, so the loop could spin retrying the same trial_id indefinitely. With MIMO occasionally dropping its YAML fence, this manifested as 12 consecutive aborts on the same trial_id 4. Fixed by replacing next_trial_id() with a sequential counter offset by the initial id. Two regression tests pin the invariant. Anthropic's earlier 20-trial run had been exposed to the same bug; the symptom was less visible because Anthropic rarely lost its YAML fence.
§ 8

What this means, and what we do next

The honest reading of the H1 verdict is uncomfortable: the LBG framework, given the SMA 20/50 baseline and a 20-trial budget, did not produce a strategy that beats buying and holding. That's a result, not a failure of execution. Three sources for the result, in priority order:

1 / data
The sealed window is hard. Split_C covers a multi-regime stretch of SPY that contains both a major drawdown and a vigorous recovery. The SMA cross was always going to be chopped up in regime changes. Buy-and-hold's sealed Sharpe of 0.861 reflects the strong tailwind a long-only equity holding gets on that window — and the SMA cross, by definition, sits out part of that rally.
2 / DSL
The action space is narrow. Single-step parameter_change / add_filter / change_sizing_mode edits cannot transform an SMA cross into a fundamentally different strategy. The framework's strongest improvement — vol-target sizing — moved train Sharpe by 0.029. The gate cannot accept a candidate this thin, and even if it did, the val window penalises any deviation from the baseline. The DSL needs more compositional edits, or the Editor needs to plan multi-trial sequences.
3 / horizon
20 trials is too few. PROPOSAL §10 sketched ~50 trials as the working budget. At our observed acceptance rate of 0 over 24 trials across both providers, even 50 wouldn't help: the Editor isn't learning to compose, just sampling local edits. The next experiment is not "more budget"; it's "better Editor priors" — either through richer skill artifacts, multi-step planning, or a structurally larger DSL.

What ships next

NextWhy
Editor multi-step planning The biggest single observed weakness. Trial-N proposals frequently reference indicators that the Editor imagined would be added in a hypothetical trial N+1. Either the prompt admits this and asks for an N-trial plan, or the orchestrator runs a Curator-style outer loop that lets the Editor see its own future-step intentions.
Built-in indicator templates Roughly 5/8 of Anthropic's trials were noop add_indicator calls — the Editor inserted RSI / ATR / regime indicators without wiring them. A small library of pre-vetted indicators (RSI, ATR, MACD, ADX, realised vol) with declared trigger semantics would let the agent reach for filter edits that actually do work.
SkillManager active mode Shadow Curator works; active Curator (Curator-proposed strategy simplifications) is gated on "the system has proven stable". We have not yet seen 10 accepted trials in a single run, so the trigger has never fired. Once it does, the strict change path for Curator-authored edits needs auditing.
Stage 4 broker adapter Out of scope for the current sprint per direction. Stage 3's PaperTradingEngine already provides the per-bar streaming surface a live broker would consume; a real adapter is a few hundred LOC plus paperwork.

The framework is built. The defenses are real. The bookkeeping is honest. The next move is on the action space, not the architecture.
