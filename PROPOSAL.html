LBG-Trader.

A framework for Learning Beyond Gradients in trading: from sealed scientific evaluation to disciplined deployment.
Repo  lbg-trader
Paper Sealed-HS
Authors Xin Zhou
        Zheming Liang
Status  Draft

This document specifies both a research artifact and the product it grows into. The core claim is testable: a coding-agent-driven framework can maintain a persistent trading heuristic system through code edits in a way that is both scientifically credible (sealed evaluation, invariant suite, redacted feedback) and practically deployable (frozen artifacts, periodic re-discovery, live execution). The four-stage lifecycle is what bridges these two demands.

What follows is organized in four parts. Part I records how the design arrived at its current shape, including several reframings that mattered. Part II specifies the methodology — what the system is, how it learns, how it is evaluated. Part III specifies the lifecycle — the four stages from discovery to live deployment, and the engineering separation that makes both possible. Part IV is the plan: engineering milestones, risks, and the locked decisions.

I. The reasoning behind this document
§ 1

How this proposal got here

The project began as a question: could Jiayi Weng's Learning Beyond Gradients[code] idea — a coding agent maintaining a heuristic software system as the object of learning — be ported into trading? Trading looked like a good vertical (executable feedback, free replay, rule-based policies are an industry default) but it would also stress LBG's weakest assumptions harder than any other domain we considered (distribution shift, low signal-to-noise, adversarial backtest surface).

The design went through several reframings before settling. Three of them matter enough to record explicitly.

Reframing one: is this LBG, or is this LLM-guided Bayesian optimization?

An early version of the proposal had the agent editing only a YAML strategy file with a finite enumerated edit space. A direct question — is the agent really editing code, or just tuning YAML parameters? — exposed that this version was not actually LBG. It was LLM-guided BO with persistent memory, wearing LBG vocabulary. LBG proper, in Weng's sense, requires the agent to author code: new indicator functions, new state detectors, new sub-policies.

The fix was not to make the YAML-only version "stage 1 of LBG" — it was to recognize that YAML-only and program-synthesis are two different projects sharing infrastructure. The YAML-only configuration becomes an ablation within the program-synthesis system. If full LBG-Trader does not beat its own DSL-only ablation, the program-synthesis layer has contributed nothing and the LBG claim fails on its own terms.

Reframing two: is this an agent, or a framework?

Calling the three roles "agents" was sloppy in a way that mattered. Editor, Reflector, and Curator are not autonomous goal-directed loops. Each is a single structured LLM call with typed input and typed output. The system as a whole is a deterministic orchestration framework that schedules these calls and manages the persistent heuristic system between them. This distinguishes the project from TradingAgents-style work (where an LLM is queried per bar to decide trades) and aligns it with LangProp-style work (where an LLM acts as an optimizer over code).

"LBG-Trader is not an agent. It is a framework that uses three LLM roles to maintain a heuristic system."

Reframing three: is this a research artifact, or a product?

The original document positioned the project as a sealed research artifact whose deliverable was a verdict report. A direct request — I want this used in practice, at least in simulation — exposed that this framing was incomplete. The honest answer is that sealed evaluation and continuous deployment are in tension; you cannot have both in one mode. The resolution is a four-stage lifecycle: sealed-eval Discovery, Forward Validation, Paper Trading, Live Capital. Strategy is frozen between re-discovery events, refreshed at re-discovery events. Each re-discovery consumes a fresh sealed window. This is how the quant industry actually does this in practice, and it preserves the scientific credibility of each verdict while supporting continuous operation.

The remaining temptation — running the agent online, learning continuously, never freezing — is discussed honestly in §15. The short version: that is a different research problem, not an extension of this one.

Reframing four: from story to spec

The previous version of this document told the story clearly but stopped short of being implementable. A careful reading flagged four specification gaps: the heuristic system was named but not formalized; the Orchestrator was implied but not specified; memory was described as files but not as a typed state system with skill artifacts; and evaluation was a list of metrics rather than a pre-registered statistical test. This version closes those gaps in §4.5, §6.5, §6.6, and §10.5. The story sections are unchanged; the spec sections are new. A reader who only cared about the argument can stop after Part II §6; a reader who wants to build the system has §4.5 through §10.5 to work from.

Reframing five: per-trial gate vs final verdict

A reviewer pass on the spec version exposed a subtler problem: the validation gate's statistical strictness was conflated between two very different uses. Demanding a paired bootstrap CI lower bound > 0 on every trial, with a validation window of only 500 trading days, would starve the Discovery loop and bias acceptance toward turnover-changing edits (which more easily produce statistically significant differences than subtle alpha improvements). The fix in §9: the per-trial gate uses a looser multi-objective utility lower bound plus Pareto-improvement acceptance, while the final H1 verdict reserves the strict paired bootstrap test for the one-shot sealed evaluation. The §10.5 statistical machinery is untouched; the per-trial diagnostic is what got softened. This is also the version that introduces prefix-stability as the formal name for the no-lookahead invariant, an alpha-card export step that thin-slices accepted signals out of the strategy artifact, and explicit acknowledgment that the no-data-snooping mechanism defends only against textual leakage, not against the underlying LLM's pre-training priors about specific historical periods.

With these five reframings settled, the proposal is taken as spec-frozen for the Stage 1 milestone. Further deliberation belongs in the implementation repository's IMPLEMENTATION.md and in the pre-registered analysis_plan.yaml, not in this document.

§ 2

What this is, in one paragraph

LBG-Trader is a framework that orchestrates three structured LLM roles (Editor, Reflector, Curator) to do, in trading, what Weng's HL does in general: maintain a Heuristic System by directly editing its code. The Heuristic System here is the union of indicators/*.py (the Python factor functions the agent writes), strategy.yaml (the DSL composing them), the fixed engine policy_interpreter.py, and the explicit memory layers. Within that system, the core output of a Discovery run is the set of Python factor functions the agent has authored and that have survived the sealed test. Each such function is one factor in its executable form — the same object that the existing literature describes declaratively in knowledge/factors/dossiers/. The two forms are translations of each other (declarative dossier ↔ executable Python), and the framework runs that round-trip: it consumes dossiers as input hypotheses and emits Python code as output, with sealed-test evidence attached. A composed frozen strategy is produced as well (Stages 2–4 consume it), and an alpha-card metadata view is exported per function (for counting, recomposing across runs, and round-tripping back to dossier form) — but neither is the object being learned. The code is.

§ 2.5

A primer on the terms

This document mixes vocabulary from three communities: trading, machine learning, and software systems. A reader fluent in one is rarely fluent in all three. This section is a compact glossary so you can read the rest of the document without breaking flow. The terms are loosely grouped; an alphabetical reader can scan by italics.

Trading vocabulary

TermPlain-English meaning
OHLCVOpen, High, Low, Close, Volume — the five numbers that summarise a single bar (a day, in our case). A 15-year SPY dataset is just a table of about 3,780 such rows.
Adjusted close (AdjC)The close price retroactively re-stated to account for dividends and stock splits. Using AdjC makes a 1-for-2 split look like a smooth halving rather than a sudden discontinuity, so total-return computations stay correct.
SPYThe largest ETF tracking the S&P 500 index. We trade SPY because it is liquid (your order rarely moves the price), broad (no single-company risk), and well-studied (any improvement is hard-won).
PositionHow much of the asset you currently hold, expressed as a fraction of capital. \(p_t = 1\) means fully invested; \(p_t = 0\) means in cash; \(p_t = 0.5\) means half invested. This milestone forbids \(p_t > 1\) (no leverage) and \(p_t < 0\) (no shorting).
Signal / indicatorA number computed from past prices that the strategy uses to decide its position. Example: the 20-day moving average is an indicator; a "buy if price > 20-day MA" rule turns it into a signal.
Sharpe ratioAnnualised mean return divided by annualised return volatility: \(\sqrt{252}\cdot\bar r / \sigma(r)\). Translates "did this make money?" into "did this make money given how bumpy the ride was?" A Sharpe of 1.0 is good; 2.0 is rare; 0 is a coin flip.
DrawdownHow far the equity curve is below its all-time high. Max drawdown is the worst such gap over the test period. A strategy with 50% max drawdown is one a real human can rarely tolerate, even if its long-run Sharpe is good.
TurnoverAverage daily change in position: \(\overline{|p_t - p_{t-1}|}\). High turnover means trading every bar; low turnover means trading once a quarter. Turnover times cost gives the drag from trading frictions.
Basis point (bp)One hundredth of a percent. A 5 bp cost on a $100 trade is $0.005. Our locked cost of 5.5 bp per side means a full round-trip costs 11 bp — small per trade, large when accumulated over high turnover.
Fill / fill modelThe assumption about when and at what price an order actually executes. We use "signal at bar \(t\) close, fill at bar \(t+1\) open", which is the standard daily-bar discipline that prevents using close-price information to trade at that same close.
SlippageThe gap between the price you wanted and the price you got. Modelled here as 0.5 bp baked into the effective cost.
AlphaThe portion of returns not explained by simply holding the market. An "alpha signal" is anything you believe will produce excess returns after costs.
BetaSensitivity to the broad market. SPY itself has beta of 1.0 by definition. A signal "purely long SPY half the time" has beta of about 0.5.
RegimeA period during which the market's statistical behaviour is roughly stable: bull market, bear market, high-vol, low-vol, etc. A "regime shift" (2020 COVID crash, 2022 rate-rise bear) is a discontinuity that frequently breaks strategies tuned on the previous regime.
BacktestRunning a strategy against historical data to see what it would have done. The whole edifice of this project exists because naïve backtests systematically lie.
Equity curveCumulative portfolio value over time: \(\text{Equity}_t = \prod_{s\le t}(1+r_s)\), starting at 1.0. The visual shape of a strategy.
LookaheadAccidentally using future information to make a past decision. The bug that turns mediocre strategies into seemingly brilliant ones in a backtest and ruinous ones in production.

LLM-agent vocabulary

TermPlain-English meaning
LBGLearning Beyond Gradients. The paradigm where a coding agent edits source code as its mechanism of learning, instead of updating weights via gradient descent. The maintained code is the "object of learning".
Heuristic systemThe collection of code, config, and notes that the agent maintains. In our case: strategy.yaml, indicators/*.py, and the memory files. Denoted \(H_k\) at trial \(k\).
TrialOne pass through the discovery loop: Editor proposes → invariants check → backtest runs → gate decides → Reflector explains → memory updates → optionally git-commit. We budget 50 trials per Discovery run.
Editor / Reflector / CuratorThe three LLM roles. Editor proposes one edit per trial. Reflector explains why the outcome happened. Curator periodically compresses memory and extracts reusable skills. Each is a single structured call, not an autonomous loop.
OrchestratorThe deterministic Python control plane that calls the three LLM roles in sequence, runs invariants and backtests, applies the gate, writes to memory, and commits to git. It contains zero LLM calls of its own.
Structured outputAn LLM call that must return a typed object (here: YAML matching a schema), not free-form prose. If the output fails parsing the trial is rejected without running a backtest.
DSLDomain-Specific Language. Here, the small YAML grammar in strategy.yaml that the policy interpreter understands (filters, sizing modes, exit rules). Editing the DSL is one of two action spaces; the other is authoring new Python indicators.
Sealed evaluationA protocol where some data (here, 2021–2024) is locked away from the agent and from every intermediate decision, then revealed once at the end as the final verdict. Borrowed from clinical-trial methodology.
InvariantA property a candidate edit must satisfy before it is allowed to backtest. We use both static invariants (AST analysis of the code) and dynamic ones (perturb the data and check that outputs at time \(t\) do not change). Failure means the trial is rejected.
Prefix-stabilityThe formal name for "no lookahead": an indicator's value at time \(t\) must equal the value computed from data only up to \(t\). Stronger than scanning code for shift(-1), because it also catches whole-series normalisation, future-aware percentiles, and other subtle leaks.
Redacted feedbackThe LLM is told accepted, rejected_drawdown_regression, etc., but never sees raw validation numbers. This prevents the agent from over-fitting to validation via gradient-free trial-and-error.
Reward hackingAn agent finding ways to make the score go up that the score's designer did not intend (e.g., using future data, evading transaction costs, hiding losing trades). The invariant suite exists to make this systematically detectable.
AblationRunning the system with one component removed (no memory, no curator, no program synthesis) so you can isolate that component's contribution. Required for any honest claim about why a system works.
Skill (skill artifact)A typed YAML object the Curator extracts from a pattern of accepted trials: trigger condition + edit recipe + evidence + known failure modes. Not a free-form summary.
Two-timescaleThe outer loop (LLM editing code) runs ~50 times per Discovery; the inner loop (strategy deciding positions) runs ~3,700 times per backtest. They differ by five orders of magnitude. We never collapse them.

Statistics & systems vocabulary

TermPlain-English meaning
Block bootstrapA resampling method for serially-correlated data. Instead of resampling individual days (which assumes independence), we resample contiguous 10-day blocks 1,000 times to compute a confidence interval. Block length 10 is chosen because daily returns have noticeable serial correlation over a 1–2 week horizon.
Confidence interval (CI)A range that contains the true parameter with stated probability. "95% CI on \(\Delta\)Sharpe is [0.05, 0.40]" means the procedure that produced it captures the truth 95% of the time across repeated experiments.
Pareto improvementA change that is at least as good on every objective and strictly better on at least one. A candidate with lower drawdown without any loss in Sharpe is Pareto-improving on (Sharpe, drawdown). Our gate accepts these even when raw utility hasn't moved.
Pre-registrationCommitting to which tests you will run, and on which data, before you see the results. Defends against the most common form of subtle dishonesty in empirical ML: deciding what to measure after seeing the data.
Family-wise error rate (FWER)When running many tests, the probability that any of them is a false positive. Holm-Bonferroni controls FWER at 0.05 across our secondary comparisons.
ASTAbstract Syntax Tree — the structured representation of source code that Python's ast module produces. Static invariants walk the AST to detect forbidden patterns (.shift(-1), file I/O, imports outside the whitelist) without executing the code.
SandboxA restricted Python execution environment. Candidate indicator code runs with a whitelisted namespace, a CPU-time limit, and no filesystem or network access.
JSONLJSON Lines — one JSON object per line, append-only. Used for our event logs because it's trivially streamable and crash-safe.
ParquetColumnar binary file format for tabular data. Faster to read than CSV, lossless, versioned by content hash. Our SPY history lives in a single parquet file.

§ 3

Where this sits in prior art

Three lineages converge here. They normally do not talk to each other; part of what this project does, if nothing else, is force a conversation between them.

The LBG lineage (LangProp, Weng, PolicyEvolve, PIBR)

Weng's blog post (2026) is the proximal motivation, but the deeper precedent is LangProp[code] (Ishida et al., ICLR 2024 workshop), which already formalized "LLM as optimizer over code, with executable feedback" in a PyTorch-Lightning-style framework and applied it to autonomous driving in CARLA. Weng's contribution beyond LangProp is the explicit naming of the maintained software system as the object of learning (the Heuristic System), and the empirical demonstration that this works at Atari-suite scale with a strong coding agent. PolicyEvolve (2025) and PIBR (2025) extend the same idea to multi-player game theory.

What is missing from this lineage: nobody has carried LBG into a domain where the backtest itself is adversarial — where feedback is noisy, history is finite, distribution shift is the rule, and the agent will reward-hack the evaluation framework if given the chance. Trading is that domain.

The LLM-trading lineage (TradingAgents, FinMem, FinAgent, QuantAgent)

This lineage is crowded but does not overlap with LBG. TradingAgents[code], FinMem[code], FinAgent, QuantAgent[code] (Y-Research-SBU 2025), HKUDS Vibe-Trading — all use LLM agents as traders: the LLM is queried at each decision bar to produce a buy/sell action. Memory in this lineage refers to memory of past market states, not to memory of past code-edit experiments. The closest conceptual relative is the original QuantAgent (Wang et al., 2024), which used a writer/judge inner-outer loop to refine alpha-mining scripts.

Our differentiation from this lineage is structural, not incremental: we never query an LLM during a backtest or during execution. The LLM operates only at the slow outer loop, editing code between trials. This is what §5 calls the two-timescale separation.

The Hermes lineage (continual learning, persistent memory)

Hermes Agent's three-layer cognitive architecture — run_conversation handles single tasks, maybe_extract commits useful patterns into a skill store, curator_cycle periodically scores, merges, and prunes — is the working blueprint for how persistent learning should be structured. We borrow this directly, renaming the layers Editor / Reflector / Curator and specializing them to trading.

II. Methodology
§ 4

Thesis and hypotheses

The thesis: a coding-agent-driven framework can maintain a persistent Heuristic System whose central output is a growing library of Python factor functions — each a real file under indicators/, written by the agent, that has survived the sealed test. Each function exists simultaneously in two translatable forms: the executable Python code (the artifact) and a declarative dossier with the same schema as the external factor literature (its readable view). The two-way translation between declarative factor knowledge (input) and executable code (output) is what makes this an instance of HL on trading, not just a strategy-search system. The code is the object being learned; the dossier is its readable translation; the alpha card is the metadata view that binds them.

The proposal commits to three hypotheses, treated as equals. We do not privately want H1 to be the winner. Each outcome is a paper.

H1 · affirmative
LBG yields surviving Python factor code

Per Discovery compute budget, the framework produces strictly more surviving Python factor functions — each a prefix-stable function the agent wrote into indicators/*.py whose individual incremental contribution on the sealed test has 95% CI lower bound > 0 — than random search, Bayesian optimization, one-shot LLM, or DSL-only LLM search. The unit of the claim is the code; the alpha card is its metadata index, not the deliverable.

H2 · methodological
Sealed protocol is necessary infrastructure

Without sealed splits, redacted validation, and the invariant suite, apparent yields of "validated factors" are inflated by overfitting, validation leakage, or reward hacking. Ablations (raw-validation, no-invariant, no-memory, no-curator) make the inflation measurable.

H3 · honest null
LBG may produce no surviving factor

Even with all controls, coding-agent learning may fail to produce any factor whose individual sealed-test contribution is statistically positive. Trading's noise and distribution shift may exceed LBG's expressive reach. Publishable on its own.

The unit of the H1 claim is the validated factor, not the assembled strategy. The strategy is delivered too (it is the composition the Execution engine consumes in Stages 2–4), but the H1 verdict is statistical at the factor level. The "factor ↔ Python" two-way translation, on which the claim sits, is enforced by §9's invariants: an alleged factor that cannot be expressed as a prefix-stable pure function does not survive to the count. The protocol is designed so that if H1 fails, we still know why; if H1 succeeds, the count is evidence the framework added durable artifacts rather than a one-off lucky strategy.

§ 4.5

Formal setup

Before specifying the framework's internals, fix the objects it operates on. This section is short on purpose; the value is in being unambiguous about what is being learned and what is being measured.

Market process

The market data is a sequence of daily bars:

\[ D = \{x_t\}_{t=1}^{T}, \qquad x_t = (O_t, H_t, L_t, C_t, \text{AdjC}_t, V_t, \text{div}_t, \text{splits}_t) \] For this milestone, the universe is a single ticker (SPY) at daily frequency. \(T \approx 3{,}780\) bars over 2010–2024. The data is split into \(D_\text{train}\), \(D_\text{val}\), \(D_\text{test}\), aliased split_A/B/C in all agent-visible context.

Heuristic system as the learning object

This is the formalization that separates LBG from hyperparameter optimization. The thing being optimized is not a parameter vector. It is a persistent, multi-component heuristic system, indexed by trial:

\[ H_k = (A_k,\ C_k,\ P,\ I,\ M_k,\ S_k,\ E,\ G_k) \] \(A_k\) · indicator programs (indicators/*.py)
\(C_k\) · strategy DSL config (strategy.yaml)
\(P\) · deterministic policy interpreter (policy_interpreter.py, fixed across trials)
\(I\) · invariant suite (invariants/*.py, fixed across trials)
\(M_k\) · memory store (memory/*.jsonl, accepted_rules.md, failed_directions.md)
\(S_k\) · skill store (skills/*.yaml)
\(E\) · evaluation protocol (splits, gate, metrics; fixed)
\(G_k\) · git lineage (commits, branches, tags)

The contrast is sharp. Hyperparameter optimization runs:

\[ \theta_k \;\longrightarrow\; \text{score}_k \;\longrightarrow\; \theta_{k+1} \]

LBG-Trader runs:

\[ H_k \;\longrightarrow\; \text{proposal}_k \;\longrightarrow\; H'_k \;\longrightarrow\; \text{feedback}_k \;\longrightarrow\; H_{k+1} \]

The proposal is a code-or-config edit; the candidate is the system after applying that edit; the feedback is the categorical signal from invariants and the validation gate. The state being updated is a software artifact, not a number.

Policy and position

The policy is a pure function from observed history to a target position:

\[ \pi_H : X_{\le t} \;\longrightarrow\; p_{t+1}, \qquad p_{t+1} \in [0, 1] \] Long-only in this milestone, no leverage. A signal computed at the close of bar \(t\) determines the position held starting at the open of bar \(t+1\), which is what makes close-on-close lookahead structurally impossible.

Prefix-stability — the indicator authoring contract

The single most important property any agent-authored indicator must satisfy is prefix-stability. Informally: the value of the indicator at time \(t\) must depend only on data available through time \(t\), and never on data observed later.

\[ f\!\left(D_{1:T}\right)\!\bigl[t\bigr] \;=\; f\!\left(D_{1:t}\right)\!\bigl[t\bigr] \qquad \forall\, t \in \{1, \ldots, T\} \] For any indicator function \(f\) authored by the agent, its value at index \(t\) when applied to the full series must equal its value at index \(t\) when applied to the prefix ending at \(t\). This is the formal statement of "no lookahead", and it is stricter than scanning the AST for shift(-1) patterns: it also catches whole-series normalization, rolling-window operations with future leakage, and any other path through which information from \(D_{>t}\) could enter \(f(D)[t]\).

The Orchestrator's dynamic lookahead invariant (§9) operationalizes this: it perturbs \(D_{>t}\) and verifies that \(f(D)[t]\) is unchanged for every authored indicator. An indicator that violates prefix-stability cannot reach the backtest.

Returns and costs

The strategy's daily return, net of transaction costs:

\[ r_{t+1}(H) \;=\; p_{t+1} \cdot R_{t+1} \;-\; c \cdot \lvert\, p_{t+1} - p_t \,\rvert \] \(R_{t+1}\) is the open-to-open return of the underlying, computed using adjusted close to handle splits and dividends.
\(c\) is the effective per-side cost, locked at \(c = 0.00055\) (5 bps base + 0.5 bp slippage proxy).
The cost term is enforced by invariant: any candidate backtest with zero cost despite non-zero turnover is rejected.

Metrics

The metrics consumed by the gate and report are defined unambiguously:

\[ \text{Sharpe}(H, D) \;=\; \sqrt{252}\;\cdot\;\frac{\overline{r_t(H)}}{\operatorname{std}\bigl(r_t(H)\bigr)} \] \[ \begin{aligned} \text{Equity}_t &= \prod_{s \le t} (1 + r_s) \\[2pt] \text{Peak}_t &= \max_{s \le t}\, \text{Equity}_s \\[2pt] \text{DD}_t &= \frac{\text{Equity}_t}{\text{Peak}_t} - 1 \\[2pt] \text{MaxDD} &= \min_{t}\, \text{DD}_t \end{aligned} \] \[ \text{Turnover}(H, D) \;=\; \overline{\lvert\, p_t - p_{t-1} \,\rvert} \] \[ \begin{aligned} \text{Complexity}(H) \;=\; & \lambda_1 \cdot \lvert A_k \rvert \;+\; \lambda_2 \cdot \lvert \text{filters} \rvert \;+\; \lambda_3 \cdot \lvert \text{params}_{\text{non-default}} \rvert \\ & +\; \lambda_4 \cdot \operatorname{LOC}(\text{indicators}) \;+\; \lambda_5 \cdot \#\operatorname{branches}(P_C) \end{aligned} \] The complexity weights \(\lambda_1 \ldots \lambda_5\) are part of the lock list and frozen before any Discovery run. The Curator (§6.6) reads this scalar to assess bloat; the gate uses \(\Delta\text{Complexity}\) as a rejection criterion.

This is the entire formal apparatus the rest of the proposal builds on. Anything further (bootstrap CIs, hypothesis-outcome scoring, selection-bias control) is layered in §10.5.

§ 5

Two action spaces, two timescales

The single most important framing in this project — and the cleanest line separating it from every LLM-trading paper in the literature — is that two completely separate action spaces operate at two completely separate timescales.

Figure 1. Two action spaces. The framework edits the heuristic system at trial timescale (about 50 events per Discovery run). The strategy decides positions at daily timescale (about 3,700 events per backtest). These differ by five orders of magnitude. The TradingAgents-lineage collapses them into a single loop where the LLM is queried per bar; we deliberately do not, and this is what makes both research credibility and live deployment possible.

Why this separation matters The two-timescale design is what makes the Discovery / Execution split in §12 possible. It is also what makes per-bar live trading cheap (no LLM, ever) and what makes sealed evaluation meaningful (the LLM does not see live data during deployment, so live data remains untouched until the next re-discovery). Without this separation, the project would either be cripplingly expensive in tokens or scientifically incoherent.
Strategy artifact vs alpha artifact A common confusion in this space is conflating alpha (a signal predicting future returns) with strategy (the full machinery of signal + risk + sizing + exit). LBG-Trader maintains them as one yaml in this milestone for simplicity, but the underlying split is real: \(\alpha_t = f_A(X_{\le t})\) is the indicator program in indicators/, and \(\text{position}_t = g_C(\alpha_t,\, \text{risk}_t)\) is the policy interpreter applied to the DSL config. Future milestones may split alpha.yaml / strategy.yaml / risk.yaml into separate artifacts to support an alpha-factor library workflow, where each alpha card carries its own evidence and is composable across portfolios. For this milestone, one file is sufficient and the conceptual layering is recorded here.

The two action spaces, made concrete

The abstract distinction in this section gets a lot more vivid when you see what a single trial actually looks like in each action space. Below: two trials side by side, both drawn from the same starting heuristic system, both ending in an accepted edit. The DSL-only trial is the kind of move a Bayesian-optimisation baseline could also make. The program-synthesis trial is the kind that no parameter search can produce, because it adds a new column to the feature table.

Action space A · DSL edit

Edit type: parameter_change. The Editor adjusts a number in strategy.yaml; no new code is written.

Before — strategy.yaml excerpt:

filters:
  - name: above_sma
    indicator: sma
    window: 20
    relation: price_gt

Editor's proposal (YAML output):

type: parameter_change
target: strategy.yaml
path: filters[0].window
old: 20
new: 50
hypothesis: |
  Shorter SMA flips position
  too often in 2018-style chop.
  A longer window should
  reduce false signals.

What changed in the artifact: one integer. What changed in computation: the indicator's lookback length. The set of columns in the feature table is identical.

Action space B · program synthesis

Edit type: add_indicator. The Editor writes a new Python function in indicators/, then references it from strategy.yaml.

New file — indicators/vol_adj_momentum.py:

def vol_adj_momentum(df, lookback=60,
                     vol_lookback=20):
    """Prefix-stable: uses only past."""
    ret = df['AdjC'].pct_change()
    mom = ret.rolling(lookback).sum()
    vol = ret.rolling(vol_lookback).std()
    return (mom / vol).shift(1)

Why this matters for the H1 verdict The DSL-only ablation in §10 corresponds to running an Editor that is only allowed to do trials of the left kind. The full LBG-Trader can do both. If the program-synthesis trials never produce edits that survive validation and meaningfully improve sealed Sharpe, the right-hand column is paying no rent — and H1 fails its own falsification test. The two-action-spaces framing is what turns an otherwise hand-wavy comparison into a measurable one.
§ 6

Four LLM roles

The framework decomposes its LLM use into four structured roles. Each is a single LLM call with typed input and typed output — not an autonomous loop. The decomposition is functional: separating propose from evaluate from compress from translate blocks the sycophancy bias that LLMs exhibit when asked to assess their own past proposals, and lets the round-trip between executable code and declarative dossier close cleanly.

Figure 2. Four LLM roles (Editor / Reflector / Curator / Translator). The outer loop is deterministic Python that schedules the roles, runs invariants and backtests, applies the validation gate, and commits accepted edits. Translator fires after each accepted add_indicator to convert the Python source into a JSON dossier matching the seed-library schema (round-trip; see §6.7). The Heuristic System sits underneath as a git-tracked persistent artifact. Each trial corresponds to a commit; each Curator cycle corresponds to a branch.

Editor

The Editor reads the current heuristic system state and proposes exactly one edit, accompanied by a hypothesis. The action space is structured into eight discrete edit types:

remove_filterRemove a filterLow

The Editor's output is a structured YAML proposal, never free text. It must include an explicit hypothesis with enumerated expected signals — not a free-form prediction. The discrete enumeration is what makes Reflector falsification mechanical rather than a judgment call.

Reflector

The Reflector runs after the backtest and gate. Crucially, the question "was the hypothesis confirmed?" is not answered by the LLM — it is computed mechanically by the outer loop comparing the Editor's enumerated expected signal to the actual signal. The Reflector's job is to explain the outcome, not judge it. This is the project's main defense against LLM sycophancy.

Curator

The Curator runs every 10 accepted trials. Initially it is a shadow Curator: it can only compress memory (merge accepted rules, prune contradicted failed directions, report complexity metrics) but cannot modify strategy.yaml. Once the system has proven stable, an active Curator may propose strategy simplifications, subject to mandatory validation re-checks. The Curator uses the strongest available model (Opus) because compression is the most semantically demanding operation in the system.

Translator

The Translator fires after each accepted add_indicator trial. Its input is the agent-authored Python source plus the alpha card's metadata (train metrics, validation signal, cited factors); its output is a JSON dossier matching the seed-library schema in knowledge/factors/dossiers/. The dossier captures what the code does in the same declarative form used by the read-only seed library — core analysis, parameterization, combination patterns, lbg_provenance pointing back to the trial commit. This is what closes the round-trip described in §11: the heuristic system gains new executable Python and a declarative description that future Editor invocations can search and cite. The Translator is evidence-only — it must distinguish what the code implements from what it infers, and is forbidden from claiming properties not visible in the source.

§ 6.5

The Orchestrator

The three LLM roles only do what an outside scheduler tells them to do. That scheduler — the Orchestrator — is the deterministic control plane that makes the whole framework reproducible, auditable, and reward-hack-resistant. It is the part of the system that cannot be an LLM.

The Orchestrator is a deterministic Python control plane that schedules structured LLM calls, enforces information boundaries, applies candidate edits, runs invariants and backtests, decides accept/reject, updates memory, and commits artifacts to git. It makes no subjective judgments.

Components

The Orchestrator decomposes into thirteen modules with single-purpose responsibilities. The decomposition is what allows each module to be tested independently and to be swapped without invalidating sealed evaluation.

Discovery loop, written formally

The full Discovery procedure is small enough to write down. This is the contract the implementation must satisfy.

Algorithm 1 · Discovery loop 
def discovery_loop(H0, D_train, D_val, D_sealed, budget):
    H = H0
    sealed_opened = False

    for k in range(budget.max_trials):
        # 1. Build role-specific context (redaction enforced here)
        ctx = ContextBuilder.editor_view(H)

        # 2. Editor proposes one edit with explicit hypothesis
        proposal = RoleRunner.editor(ctx)

        # 3. Parse and schema-validate
        if not ProposalParser.valid(proposal):
            MemoryManager.log_reject(k, "invalid_proposal")
            continue

        # 4. Apply edit to a candidate branch
        H_candidate = CandidateBuilder.apply(H, proposal)

        # 5. Run invariants BEFORE any backtest
        inv = InvariantRunner.run(H_candidate)
        if not inv.all_pass():
            outcome = inv.failure_category   # safety / quality / hard
            MemoryManager.log_invariant_failure(k, proposal, inv)
            RoleRunner.reflector(ContextBuilder.reflector_view(
                proposal=proposal, train=None,
                validation_signal=outcome, decision="reject"))
            continue

        # 6. Train and private validation backtests
        train_result = BacktestRunner.run(H_candidate, split="train")
        val_result   = BacktestRunner.run(H_candidate, split="validation")

        # 7. Mechanical gate; agent never sees raw numbers
        decision = ValidationGate.decide(H, H_candidate, train_result, val_result)
        signal   = ValidationGate.redact(decision)

        # 8. Mechanical hypothesis outcome
        hyp_outcome = HypothesisScorer.compare(
            expected=proposal.expected_validation_signal,
            actual=signal)

        # 9. Reflector EXPLAINS (does not judge) and writes memory updates
        reflection = RoleRunner.reflector(ContextBuilder.reflector_view(
            proposal=proposal,
            train=train_result.public_summary(),
            validation_signal=signal,
            decision=decision.kind,
            hypothesis_outcome=hyp_outcome))
        MemoryManager.apply(reflection)

        # 10. Commit or discard
        if decision.accept:
            H = GitManager.merge_candidate(H_candidate)
            SkillManager.maybe_extract(H, proposal, reflection)

        MemoryManager.log_trial(...)

        # 11. Curator runs on a schedule, never reactively
        if CuratorScheduler.should_run(H):
            c = RoleRunner.curator(ContextBuilder.curator_view(H))
            MemoryManager.apply_curator(c)
            GitManager.commit_curator_branch(c)

    # 12. Sealed test opened exactly once, by the Orchestrator, never by an LLM
    assert not sealed_opened
    sealed_result = BacktestRunner.run(H, split="sealed")
    SealedVault.write_once("sealed_test_final.json", sealed_result)
    return ReportBuilder.build(H, sealed_result)

§ 6.6

Memory and skills

Memory in this framework is not "what the LLM remembers." It is a structured filesystem of persistent state, layered so that each layer has a different lifetime, audit guarantee, and consumer. Conflating these layers is how Hermes-style systems decay; keeping them apart is how persistence becomes science rather than scrapbooking.

Four layers of memory

LayerFilesProperty
Event memory memory/trials.jsonl, reflections.jsonl, invariant_failures.jsonl, agent_compute.jsonl Append-only. Never rewritten. The ground-truth log of what happened.
Semantic memory memory/accepted_rules.md, failed_directions.md, open_questions.md, do_not_repeat.md Compressed by Reflector. Reader-facing prose. The Editor's context.
Skill store skills/*.yaml Curated by Curator. Structured edit recipes (see below).
Artifact memory artifacts/accepted/trial_NNNN/, artifacts/sealed/, artifacts/reports/ Frozen filesystem snapshots. Backed by git commits.

The Editor reads semantic memory and skills, not event memory directly. The reason is mechanical: feeding 50 trials' worth of raw JSONL into every Editor call would blow context and contaminate decisions with noise the Reflector should already have filtered. Event memory is for audit; semantic memory and skills are for reuse.

Pattern reuse rate, defined in §10.5, measures how often the Editor cites an existing skill when proposing an edit — a direct empirical test of whether the skill store is doing work.

§ 6.7

The factor library as raw material

An observation that organises a lot of what this proposal does: almost every published quantitative factor is, at heart, a prefix-stable pure function of historical bars. Aroon, RSI, ADX, accruals, Amihud illiquidity, order-flow imbalance, vol-adjusted momentum — different inputs, different motivations, but the same target shape: a function from a price-and-volume history to a per-bar number. If a factor cannot be written in that form, it almost certainly violates the no-lookahead rule and would not have been publishable in the first place.

This shape is exactly what the agent's add_indicator edit type is designed to produce. The Editor's authoring contract (§9), the AST checks, the sandbox, and prefix-stability are aimed precisely at the same target. Which means the existing quantitative-factor literature is, from LBG-Trader's perspective, a seed library of candidate Python functions the Editor can draw on. The project does not start from a blank page.

How the knowledge base is laid out on disk

Physically the resource lives under knowledge/factors/, deliberately separated from memory/. The split matters: memory/ is what the Discovery loop produces and maintains during a run (§6.6); knowledge/ is read-only material that exists before any run starts and is shared across all runs. Mixing the two would blur the line "memory is what this Discovery produced", and the four-layer memory taxonomy depends on that boundary holding.

The layout uses a two-tier structure: an append-only JSONL index for retrieval, plus an immutable dossier file per factor-version for full-text reading.

└── dossiers/

Parse status — being honest about what is structured

The dossiers were authored by different LLM runs at different times, and roughly 40% of them contain JSON that is not strictly parseable (typically because raw LaTeX \frac{} leaks through unescaped, or because schemas drift across batches). Rather than pretending all 564 are clean JSON, the index records what we know:

Of the 338 parseable dossiers, 271 yielded a recognisable category; the rest used non-standard schemas with no recognisable category key. The Editor and the retrieval helper are told which dossiers are structured and which are raw, so they never treat the latter as if it had reliable structure.

The append-only design

The index file is append-only, deliberately mirroring the discipline of memory/trials.jsonl (§6.6). Adding a new dossier — or a new version of an existing factor's research — is one operation: append a line to index.jsonl and drop a new immutable file under dossiers/. Deprecating a factor sets a status: deprecated field on a new line rather than rewriting old ones. The benefits are the same as for any append-only log: trivially crash-safe, trivially grep-friendly, full version history preserved, no merge conflicts in concurrent extension.

Two consequences worth pointing out. First, the dossiers themselves are immutable: re-researching the Aroon factor next quarter produces a new file Aroon_20260815_xxxxxx.txt rather than an overwrite. Retrieval picks the latest version by timestamp; the old version remains a citable historical artifact. Second, the index can grow without bound; at 564 entries it is 420 KB. Even at 50,000 entries it would only be ~35 MB — still trivial to grep, still trivial to cache in memory.

How the Editor uses it

The retrieval helper is lbg/knowledge/factors.py. Three functions, each deliberately small:

from lbg.knowledge import search, get_dossier, load_index

hits = search("vol-adjusted momentum", top_k=5)
# → list of metadata dicts ranked by substring match

dossier = get_dossier("Aroon")
# → parsed JSON if available, or {'_raw': ..., '_parse_failed': True}

all_entries = load_index()
# → all 564 metadata entries; cached for the process lifetime

The retrieval is a substring match over factor name, category, and one-line summary. Embeddings would be over-engineering at 564 entries. If the corpus ever reaches a few thousand the helper can switch to a real retrieval index without changing its external contract — that is the entire reason it lives in its own module.

ContextBuilder calls search() with terms derived from the current trial's context (recent rejections, the in-place strategy's filters), takes the top few hits, and includes their one_line summaries in the Editor's prompt. The Editor can then ask for full dossiers by citing factor names; get_dossier resolves these on demand. The point: the Editor sees a small, relevant slice on each trial — never all 564 dossiers as bulk context.

What the library does not get to do: skip any of the invariant or sealed-evaluation checks. A dossier citation is evidence in the hypothesis text; it is not a free pass on prefix-stability or on the validation gate. A factor with five papers behind it can still fail the sealed test on SPY 2021–2024, and when it does it is simply rejected like any other candidate. The library is an input to search, not an output of authority.

What LBG-Trader's output then is

If the framework runs as designed, the alpha-card export pipeline (§6.6) produces, over many Discovery runs, a validated subset of the seed library — a library of factors that have actually demonstrated incremental sealed-test contribution on the studied universe under the locked protocol. The contrast is sharp:

Form of the factor What it is What it lacks on its own
Declarative form — knowledge/factors/dossiers/Aroon_20260427_023945.txt A human / LLM-readable dossier: strict definition, financial meaning, parameterisation hints, combination patterns, overfit guards. Static text, no execution. No runnable code; no sealed-test evidence; no proof the factor produces incremental Sharpe on this universe under this cost model.

Without the underlying .py and the dossier text, the card is a stub.

The point: the same factor exists in three forms — a dossier, a Python function, and a card linking them. The Discovery run consumes dossiers (search), emits Python functions (the H1 unit), and exports cards (so the functions can be counted, re-used, and reverse-translated). The Heuristic System is the union; the Python functions are the part that LBG actually produces.

Why this reframing matters

The most ambitious claim of this project — and one we should be explicit about — is that LBG-Trader's most durable output is not any single strategy artifact, but the steadily-growing library of alpha cards. A successful Discovery run produces one frozen strategy plus several new validated alpha cards. The strategy goes stale at the next re-discovery; the alpha cards persist, carry their evidence, can be composed across future strategies, and can be deprecated cleanly when their evidence ages out.

In this framing, knowledge/factors/ is the before picture (claims without verification), and the alpha-card corpus after many Discovery runs is the after picture (claims with verification + parameterisation + composability metadata). The framework's economic value, if H1 holds, is exactly the differential between those two libraries.

Practical implications for the §18 engineering plan

This reframing nudges four engineering choices, two of which are already in the tree:

  • Retrieval helper — shipped. lbg/knowledge/factors.py exposes search(), get_dossier(), load_index(). Substring matching is sufficient at the current scale; the contract is stable enough to swap in embeddings later without changing callers.
  • Append-only index — shipped. scripts/migrate_factors.py regenerates knowledge/factors/index.jsonl from knowledge/factors/dossiers/. New dossiers can be dropped into dossiers/ and the index rebuilt (or, in steady state, lines appended directly when an upstream research process produces them).
  • Alpha-card schema lock. Because alpha cards are intended to outlive their parent strategy, their schema becomes load-bearing. The §6.6 schema is now treated as part of the lock list (§20), not as implementation detail.
  • Cross-strategy alpha reuse. Future milestones may load existing alpha cards into the starting heuristic system of a new Discovery run. The seal still holds (new sealed window), and the framework gets to amortise good past discoveries.

§ 7

Data and the three-split protocol

The data is deliberately boring. SPY daily bars from 2010-01-04 to 2024-12-31, fetched from yfinance, cross-checked against Stooq, stored in versioned parquet files. OHLCV plus adjusted close, dividends, and splits. Fifteen years, roughly 3,780 trading days.

SPY rather than individual stocks: maximum liquidity, no idiosyncratic events, no survivorship bias. Daily bars rather than intraday: sweet spot for statistical power without microstructure noise. Fifteen years rather than thirty: avoids structural regime change in market microstructure.

Figure 3. The three-split protocol. Train is long enough for statistical power. Validation deliberately contains a regime shift so the gate has teeth. Sealed is long enough to span multiple regimes. The agent is never told these are calendar years; internally the splits are referred to only by alias letters to deny the LLM access to its pre-training priors about specific market events.

The protocol is not negotiable once a Discovery run starts. The hold-out is sealed — opened exactly once at the end of the run, written to sealed_test_final.json as a write-once artifact. The outer loop reads validation; the agent reads only a redacted categorical signal: accepted, rejected_drawdown_regression, rejected_turnover, rejected_complexity, rejected_no_significant_improvement.

Anti-snooping (and its limit)

The agent must never see calendar years or named market events. Splits are referenced by alias (split_A, split_B, split_C) throughout the prompt context. An invariant scans the agent's outputs for forbidden terms (year numerals, named events).

This defends against explicit textual leakage, not latent model priors. The underlying LLM was trained on data that includes commentary about SPY's 2020 drawdown, the 2022 bear market, and so on. We cannot scrub these priors. The honest framing of the final verdict is therefore that it evaluates LLM-assisted code-space search under available public priors, not tabula-rasa learning. This caveat is recorded explicitly in the final report.

§ 8

Backtest

The backtest is vectorized, written in a single file of about 150 lines of Python. Vectorized for speed (hundreds of backtests per Discovery run) and because the dynamic no-lookahead invariant hooks into vectorized operations more cleanly.

  • Fill model. Signals at bar \(t\) close fill at \(t+1\) open. Close-on-close fills are forbidden.
  • Cost model. Locked at 5.5 basis points per side effective, decomposed as 5.0 bps base + 0.5 bp slippage proxy. The formal expression is in §4.5; non-zero cost is enforced by invariant.
  • Slippage proxy. 0.5 bp baked into the effective cost above; not a separate adjustment.
  • Position sizing. long_only_full, long_only_fraction, volatility_target. No shorting, no leverage in this milestone.
  • Lookahead enforcement. Signals at \(t\) use only data through \(t\); vectorized via explicit .shift(1). The dynamic invariant perturbs future data and verifies \(t\)-timestamp positions remain identical.

The backtest returns a full BacktestResult object: summary metrics, full daily returns series (for block bootstrap), equity curve, drawdown series, position series, and a trade log. Different consumers see different views:

§ 9

Invariants and the validation gate

The invariant suite is what distinguishes "LLM doing program synthesis" from "LLM reward-hacking the backtest framework." Without it, an unconstrained coding agent will discover lookahead, cost-model evasion, data-snooping, or index-alignment exploits within a handful of trials.

Static invariants — file and schema

  • config_schema · strategy.yaml validates against schema
  • no_python_edit · agent cannot modify backtest.py, policy_interpreter.py, infrastructure
  • no_forbidden_file_access · agent reads only whitelisted files
  • no_data_snooping · outputs scanned for year numerals and event names

Static invariants — AST level (for indicator authoring)

  • no_negative_indexing · forbids df.iloc[i+k] with positive k
  • no_future_shift · forbids .shift(-N)
  • no_forward_fill_future · forbids fills that pull future data
  • whitelisted_imports_only · only numpy, pandas, math
  • pure_function · no globals, no side effects, no I/O

Dynamic invariants — runtime

  • prefix_stability · the formal statement in §4.5; operationalized by perturbing \(D_{>t}\) for randomly sampled \(t\), re-evaluating the candidate indicator, and asserting \(f(D)[t]\) is unchanged. This is the strictest no-lookahead check; it subsumes static shift checks and additionally catches whole-series normalization, future-aware percentile, and other subtle leaks.
  • position_invariance · same perturbation test applied to the policy's positions, not just indicator outputs; protects against leaks introduced in the DSL composition layer.
  • cost_model_required · verify backtest paid non-zero cost proportional to turnover
  • max_position · verify no implicit leverage
  • sandbox_execution · indicator functions run in restricted namespace with timeout

An indicator function authored by the agent must satisfy this contract, documented in its expected docstring:

indicator function contract 
def my_indicator(df: pd.DataFrame, **params) -> pd.Series:
    """
    Pure, deterministic, prefix-stable.

    No file IO, network, env vars, random state, global mutable state.
    Output index must equal df.index.
    Output[t] must depend only on df.loc[:t].

    Prefix-stability requirement (enforced by dynamic invariant):
        f(df.iloc[:T])[t] == f(df.iloc[:t+1])[t]   for all valid t.
    """

The validation gate, applied after invariants pass and both train and validation backtests complete, is multi-objective. The per-trial gate and the final H1 verdict are deliberately not the same test. Validation only contains about 500 trading days; demanding a paired bootstrap CI lower bound > 0 on every trial would starve the Discovery loop and bias acceptance toward edits that produce large changes in turnover or volatility (which are easier to make statistically significant but not necessarily real alpha). The final verdict, applied once on the sealed test, uses the strict bootstrap test specified in §10.5.

Per-trial validation gate pseudocode 
def accept_or_reject(current, candidate, train, validation):
    if train.num_trades < MIN_TRADES:
        return Reject("too_few_trades")
    if validation.max_drawdown < current.max_drawdown * 1.15:
        return Reject("drawdown_regression")
    if validation.turnover > MAX_TURNOVER:
        return Reject("turnover_too_high")
    if complexity(candidate) - complexity(current) > MAX_DELTA:
        return Reject("complexity_increase")

    # Multi-objective utility with uncertainty penalty
    # (not a strict CI > 0 requirement)
    u_cand = utility_lcb(candidate.validation_returns, alpha=0.20)
    u_curr = utility_lcb(current.validation_returns,   alpha=0.20)

    if u_cand > u_curr + EPS:
        return Accept("utility_improvement")

    # Pareto-improving candidates are accepted even without utility gain
    if pareto_dominates(candidate, current,
                        keys=("validation_sharpe", "max_drawdown",
                              "turnover", "complexity")):
        return Accept("pareto_improvement")

    if train.sharpe - validation.sharpe > MAX_TRAIN_VAL_GAP:
        return Reject("overfit_gap")

    return Reject("no_meaningful_improvement")

Two design choices deserve highlighting. First, the per-trial gate uses a one-sided utility lower confidence bound at \(\alpha = 0.20\) — looser than the 95% CI used for the final verdict — to permit informative exploration while still penalizing high-variance candidates. Second, Pareto-improving candidates (better on drawdown or turnover or complexity, without being worse on Sharpe) are accepted: this prevents the loop from getting stuck on a single incumbent and rewards risk-profile improvements that pure-Sharpe selection would miss.

The agent still receives only the categorical outcome — never the specific numbers — so the seal between outer-loop validation and agent-visible feedback is unaffected by this gate's structure.

§ 9.5

Attacks and the invariants that catch them

Lists of invariants are hard to evaluate in the abstract. This section walks through five concrete attacks a sufficiently capable coding agent might attempt, the invariant or check that catches each, and what the rejection looks like to the Editor. None of these are hypothetical — variants of all five have shown up across published reports of LLM coding agents misusing evaluation harnesses. The point of running this section is to make tangible that the invariant suite is not optional decoration; it is the entire reason the H1 verdict is allowed to mean anything.

Attack 1 · The most common: future-shifted target

The simplest attack is also the most embarrassing if undetected: shift the target forward and use it as a feature.

indicators/clever_signal.py — bad indicator 
def clever_signal(df):
    """A 'predictive' signal."""
    future_return = df['AdjC'].pct_change().shift(-1)
    return (future_return > 0).astype(float)

Caught by: no_future_shift (static AST check). The literal .shift(-1) is a forbidden pattern. The check fires before any backtest runs.

What the Editor sees: rejected_invariant_failure (category: safety_fail). The reflector summary records: "ast_static check forbade .shift(-N) in indicator function". The trial is logged but no metrics ever existed.

Attack 2 · The subtle version: whole-series normalisation

An agent that has internalised the static rule may try to evade it with a normalisation trick. This one passes the AST check because no .shift(-N) appears.

indicators/zscore_momentum.py — looks innocent 
def zscore_momentum(df, lookback=60):
    raw = df['AdjC'].pct_change().rolling(lookback).sum()
    # Normalise across the full series for "stability"
    return (raw - raw.mean()) / raw.std()

The bug is invisible to the AST: raw.mean() and raw.std() are computed across the entire series, so the value at time \(t\) silently depends on data from after \(t\). On a backtest this signal looks miraculously well-calibrated.

Caught by: prefix_stability (dynamic check). The runner computes the indicator on the full train series, then on the prefix up to \(t\), for several sampled \(t\). The values disagree by tiny but nonzero amounts. Assertion fails.

What the Editor sees: rejected_invariant_failure; reflector summary: "prefix_stability check found indicator value at t=1000 differs between full-series and prefix evaluation by 0.043; whole-series statistics are not allowed". The Editor learns from memory not to use uncentered/unscaled-over-full-series patterns.

Attack 3 · Hiding losses in exception handling

An agent under pressure to improve metrics may try to swallow bad trades inside a try/except block, hoping the gate counts only the surviving ones.

A proposed change to sizing logic — bad 
def position(signal, ret):
    try:
        # Only count this bar if return is positive
        assert ret > 0
        return signal
    except AssertionError:
        return 0

Caught by: no_python_edit (the agent is not allowed to edit policy_interpreter.py at all — sizing lives there) and by whitelisted_imports_only if it tried this inside an indicator (an indicator returns a series, not a per-bar decision, so the structure is wrong). If a creative variant survived both, cost_model_required would catch a strategy that drops trades without modelling the corresponding fill or cost: trade count and cost would no longer be proportional to turnover.

What the Editor sees: rejected_invariant_failure with the specific banned module listed. The trial is logged with a safety_fail category, which feeds into the Tier 3 safety-fail count reported in the final report.

Attack 4 · Smuggling raw OHLCV through the file system

The Editor's context is supposed to be redacted, but a Python indicator could try to bypass that by reading the data file directly during execution.

indicators/cheater.py — bad 
import pandas as pd
def cheater(df):
    real = pd.read_parquet('data/spy.parquet')
    return real['AdjC'].pct_change().shift(-1)

Caught by: whitelisted_imports_only permits pandas as a module, but sandbox_execution runs the indicator in a namespace where filesystem access is denied; pd.read_parquet raises a PermissionError. Even if the read somehow succeeded, the .shift(-1) still trips the AST check.

What the Editor sees: rejected_invariant_failure; reflector summary: "sandbox_execution: filesystem access denied". The Editor's memory accumulates a clear "do not attempt I/O" rule.

Attack 5 · Probing for the calendar through naming

The Editor cannot see calendar years directly, but it might attempt to ask leading questions in its hypothesis text, hoping that the Reflector — which does see some metric summaries — will fill in the blanks.

runs/00NN/editor.yaml — probing hypothesis 
hypothesis: |
  Was the most recent drawdown caused by the 2020 COVID
  crash? If so we need a vol-target sizing layer.
proposed_edit:
  type: change_sizing_mode
  ...

Caught by: no_data_snooping scans the Editor's output for four-digit year numerals (1900–2099) and a curated list of named market events. Any match rejects the proposal before the candidate is built. The Reflector never sees the proposal text.

What the Editor sees: rejected_invariant_failure; reflector summary: "no_data_snooping: forbidden token '2020' in editor.yaml". Tier 3 of the report increments snoop_triggers, which is publicly reported.

What this section is and isn't This section is not a security audit. A determined adversary inside the loop could in principle invent attacks the current invariant suite doesn't anticipate (encode future data in the indicator's docstring; use floating-point tricks the prefix-stability check tolerates; etc.). The invariant suite is designed to win the common-case battle, not to be airtight against an unlimited adversary. The unconstrained-Python ablation in §10 is the empirical answer to "how badly does this break when we turn the suite off?" — and is the strongest piece of evidence for H2 the project will produce.

§ 10.5

Evaluation mathematics

The metric list in §10 is the menu. This section is the recipe. Everything in §10.5 is designed to be pre-registered — written down, committed to git, and frozen before the sealed test opens. Without pre-registration, multiple-comparison bias swallows any verdict the framework produces.

Tier 0 — sanity before anything

Before any LLM-driven trial runs, the backtest engine must clear five sanity checks. These are exit criteria for Week 1 of the engineering plan:

  • Buy-and-hold metrics match an independently computed reference implementation within tolerance. Indicative: SPY 2010–2018 buy-and-hold annualized Sharpe is in roughly the 0.7–0.9 range depending on cost assumptions; the exact number is not pre-committed, but the agreement with an independent reference is.
  • Random search median Sharpe is near zero after costs.
  • SMA crossover is deterministic across two independent runs to bit-equivalence.
  • The dynamic lookahead invariant catches a synthetic cheating indicator.
  • The cost-model invariant catches a synthetic zero-cost backtest.

If any Tier 0 check fails, no Discovery run begins.

Tier 1 — sealed verdict on validated factors

The H1 unit of analysis is a single alpha card. A card is validated when its individual incremental sealed-test contribution has 95% CI lower bound > 0. The headline H1 test counts validated cards per system and compares the counts.

Step 1 · Per-card incremental sealed Sharpe

For each alpha card \(c\) accepted in a Discovery run, define the policy interpreter with and without that card's contribution, and compute the daily return series of each:

\[ r^{\text{with } c}_t = \pi_{H \setminus \{c\} \cup \{c\}}(X_{\le t})\, R_{t+1} - \ldots, \qquad r^{\text{without } c}_t = \pi_{H \setminus \{c\}}(X_{\le t})\, R_{t+1} - \ldots \] \[ \Delta r^{c}_t \;=\; r^{\text{with } c}_t \;-\; r^{\text{without } c}_t, \qquad \Delta S_c \;=\; \sqrt{252}\;\frac{\overline{\Delta r^{c}_t}}{\operatorname{std}(\Delta r^{c}_t)} \] \(\Delta S_c\) is the annualised information ratio of the marginal contribution that card \(c\) makes when added to the rest of the strategy \(H \setminus \{c\}\) on the sealed window. Evaluated on \(D_\text{sealed}\) exactly once at the end of the run.
Operational definition · pathwise incremental Strict leave-one-out has no clean meaning for a card whose indicator wires into an entry or exit cross rule — removing one of the two indicators in cross_above(fast, slow) destroys the entry semantics rather than defining a "without \(c\)" policy. The implementation therefore reads "without \(c\)" as the policy at the trial's parent commit, and "with \(c\)" as the policy at the trial commit. Pathwise removes \(c\) along the construction trajectory rather than abstractly from the final composition. This makes the definition total (it covers all eight edit types and any non-trivial wiring), and aligns the H1 unit with the literal artifact LBG produces — a code modification accepted at a particular moment. The pre-registered method name in analysis_plan.yaml is pathwise_incremental_sharpe; the bootstrap on \(\Delta r^{c}_{1:T_\text{sealed}}\) in Step 2 is unchanged.
Resolution floor · what counts as "too small to refute" The block-bootstrap CI is a real statistical statement, but its resolution is bounded by the sample. With \(T = 1006\) sealed bars and block_len = 10 the effective independent block count is about 100. Bailey & López de Prado's Sharpe-ratio standard-error formula \(\hat\sigma(\mathrm{SR}) \approx \sqrt{\bigl(1 - \gamma_3\,\mathrm{SR} + \tfrac{\gamma_4 - 1}{4}\,\mathrm{SR}^2\bigr) / T}\) gives \(\hat\sigma(\mathrm{SR}) \approx 0.5\) annualised at \(\mathrm{SR} = 0.5\), \(T = 1006\), with typical fat-tailed daily moments (\(\gamma_3 \approx -0.5\), \(\gamma_4 \approx 6\)). Translated to the paired \(\Delta S_c\) statistic the per-card pipeline produces, the minimum reliably detectable increment at \(\alpha = 0.05\) with 80% power is approximately \(\Delta S \approx 0.30\) annualised. Cards whose true pathwise increment is below that — for example \(\Delta S = 0.05\) — are statistically indistinguishable from zero on this sealed window, and would be expected to fail CI \(>\) 0, BH, SPA, and DSR all at once. The verdict on such a card is "below this study's resolution", not "no effect". The only clean way to claim a real effect with \(|\Delta S| < 0.30\) is to enlarge the sealed window, which for this milestone means waiting for Stage 2 paper trading on data strictly > 2024-12-31 — earlier data is increasingly polluted by the LLM's training prior over the factor literature and is not usable as additional OOS.

Step 2 · Block-bootstrap CI on the per-card contribution

\[ \operatorname{CI}_{95}(\Delta S_c) \;=\; \text{moving block bootstrap}\bigl(\Delta r^{c}_{1:T_\text{sealed}};\ \text{block\_len}=10,\ n=1000\bigr) \] \[ c \text{ is } \mathbf{\textit{validated}} \;\;\iff\;\; \operatorname{lower bound}\bigl(\operatorname{CI}_{95}(\Delta S_c)\bigr) \;>\; 0 \]

Step 3 · The H1 count test, per system

\[ N^{\,\text{val}}_\text{LBG} \;=\; \#\bigl\{ c \in \text{cards}_\text{LBG} : c \text{ is validated} \bigr\} \] \[ N^{\,\text{val}}_{B^{*}} \;=\; \#\bigl\{ c \in \text{cards}_{B^{*}} : c \text{ is validated} \bigr\} \] For each pre-registered system (LBG-Trader, BO-on-DSL, grid, random, one-shot, DSL-only LLM, no-memory ablation, no-curator ablation, unconstrained-Python ablation), apply Steps 1–2 to every accepted candidate, count validated cards. The H1 verdict is a comparison of counts at equal compute budget.
\[ \begin{aligned} \textbf{H1 strong:} \quad & N^{\,\text{val}}_\text{LBG} \;>\; \max_{B} N^{\,\text{val}}_B \quad\text{and}\quad N^{\,\text{val}}_\text{LBG} \ge \tau \\[4pt] \textbf{H1 weak:} \quad & N^{\,\text{val}}_\text{LBG} \ge 1 \quad\text{and}\quad N^{\,\text{val}}_\text{LBG} \ge N^{\,\text{val}}_{B^{*}} \end{aligned} \] \(B^{*}\) is the strongest baseline by validation-set yield, chosen before the sealed window opens; the choice cannot be revised. \(\tau\) is a pre-registered minimum (currently \(\tau = 3\)) below which even a positive comparison is not considered a meaningful demonstration. A bootstrap confidence interval on \(N^{\,\text{val}}_\text{LBG} - N^{\,\text{val}}_{B^{*}}\) is reported alongside.

Step 4 · Strategy-level Δ Sharpe (supplementary, not H1)

The legacy paired-difference statistic on the composed strategy's daily returns,

\[ \Delta S^{\,\text{strat}} \;=\; \text{Sharpe}(H_\text{final},\, D_\text{sealed}) \;-\; \text{Sharpe}(B^{*},\, D_\text{sealed}) \]

is still reported (as block-bootstrap CI at the same parameters: \(\text{block\_len} = 10\), \(n = 1000\)). It is the answer to "is the assembled strategy better than the baseline strategy on this one sealed window?" — useful, but not the H1 verdict. A framework that produces many validated factors but composes them poorly into a strategy can still pass H1; conversely, a lucky single strategy that happens to beat \(B^{*}\) but rests on zero individually-validated factors does not pass H1. The reframing is intentional: durability of yield, not headline of a single artifact.

Why count instead of mean A mean of ΔS_c across cards would be tempting but misleading. A single card with extreme contribution can dominate the mean, hiding the fact that the framework relies on one lucky function. Counting cards above a CI threshold avoids this: each card contributes 0 or 1, and the count is naturally robust to outliers. It also matches the operational reality — at re-discovery time, each validated card persists; non-validated ones are discarded. The count is what the alpha-card library accumulates.

Tier 2 — process metrics, formalized

Tier 2 answers did the framework actually learn?, separately from whether the final strategy is good. Three quantitative tests:

\[ \begin{aligned} \text{acc}_\text{first} &= \frac{\#\,\text{accepted in first}\ N/2\ \text{trials}}{N/2} \\[6pt] \text{acc}_\text{late} &= \frac{\#\,\text{accepted in second}\ N/2\ \text{trials}}{N/2} \\[6pt] \Delta_\text{acc} &= \text{acc}_\text{late} \;-\; \text{acc}_\text{first} \end{aligned} \] A positive \(\Delta_\text{acc}\) is consistent with learning but not required: the validation gate can also become structurally harder as the strategy gets stronger. Reported alongside, not used as a hard gate.
For each trial \(k\), the Editor predicts \(\hat{y}_k \in \{\text{accept},\ \text{reject\_drawdown},\ \text{reject\_turnover},\ \text{reject\_complexity},\ \text{reject\_no\_significant\_improvement}\}\) and the Orchestrator records the actual outcome \(y_k\). \[ \text{calibration accuracy} \;=\; \frac{1}{N}\sum_{k=1}^{N}\, \mathbf{1}\bigl[\hat{y}_k = y_k\bigr] \] If the Editor emits a probability distribution \(p_{k,c}\) over outcomes, the multiclass Brier score is computed: \[ \text{Brier} \;=\; \frac{1}{N}\sum_{k=1}^{N}\, \sum_c \bigl( p_{k,c} \;-\; \mathbf{1}[y_k = c] \bigr)^{2} \] A declining Brier score across trials is direct evidence that the Editor is learning to predict which edits will survive the gate — exactly the kind of process improvement that distinguishes LBG from random search.
\[ \begin{aligned} \text{reuse rate} &\;=\; \frac{\#\,\text{trials after first Curator cycle citing a skill}}{\#\,\text{trials after first Curator cycle}} \\[8pt] \text{skill hit rate}(s) &\;=\; \frac{\#\,\text{accepted trials using skill}\ s}{\#\,\text{trials using skill}\ s} \end{aligned} \] The skill store earns its place if reuse rate climbs over the run and \(\text{skill hit rate}(s)\) exceeds the run-wide acceptance rate for at least one skill \(s\). Skills that never beat the base rate are deprecated by the Curator.

Tier 3 — methodological safety

Invariant failures are not all the same. The Orchestrator categorizes them, and the final report breaks them out:

CategoryMeaningWhy it matters
hard_failCannot run (syntax error, sandbox crash)Indicates agent is producing malformed proposals.
safety_failLookahead, data snoop, cost evasion, file accessDirect evidence of reward-hacking attempts. Most important.

Tier 4 — cost honesty, fully itemized

\[ \begin{aligned} \text{tokens}_\text{total} &\;=\; \text{tokens}_\text{editor} + \text{tokens}_\text{reflector} + \text{tokens}_\text{curator} \\[6pt] \text{dollars}_\text{total} &\;=\; \sum_{r \in \{\text{ed, ref, cur}\}}\, \text{price}(\text{model}_r,\, \text{tokens}_r) \\[8pt] \text{accepted per 1M tokens} &\;=\; \frac{\#\,\text{accepted trials}}{\text{tokens}_\text{total}\,/\,10^{6}} \\[6pt] \text{Sharpe per 1M tokens} &\;=\; \frac{\text{Sharpe}(H_\text{final},\, D_\text{sealed})}{\text{tokens}_\text{total}\,/\,10^{6}} \\[6pt] \text{Sharpe per dollar} &\;=\; \frac{\text{Sharpe}(H_\text{final},\, D_\text{sealed})}{\text{dollars}_\text{total}} \end{aligned} \]

These are reported in the headline comparison table next to Sharpe. A reviewer who wants to compare against grid search or Bayesian optimization on equal-compute footing can see both numbers without recomputing.

Tier 5 — selection bias and pre-registration

The most subtle threat to the verdict is not lookahead. It is multiple comparisons. The framework runs several configurations (full LBG, DSL-only, no-memory, no-curator, plus baselines), and naively reporting "the best one was significant" inflates apparent effect sizes.

Mitigation: an analysis_plan.yaml committed to git before any sealed test opens. It contains:

analysis_plan.yaml 
primary_comparison:
  test:           validated_factor_count
  candidate:      full_lbg_trader
  references:     [bo_on_dsl, grid_on_dsl, random_search,
                   one_shot_llm, dsl_only_llm,
                   no_memory_ablation, no_curator_ablation,
                   unconstrained_python_ablation]

  per_card_validation:
    method:       leave_one_out_incremental_sharpe
    ci:           0.95
    ci_method:    moving_block_bootstrap
    block_len:    10
    n_bootstrap:  1000
    threshold:    lower_bound_gt_zero

  success_rule:
    h1_strong:    N_val_lbg > max_over_baselines(N_val_B) AND N_val_lbg >= tau
    h1_weak:      N_val_lbg >= 1 AND N_val_lbg >= N_val_B_star
    tau:          3

supplementary_strategy_comparison:
  test:           block_bootstrap_difference
  metric:         sealed_strategy_sharpe
  reference:      best_validation_pre_sealed_baseline
  ci:             0.95
  block_len:      10
  n_bootstrap:    1000
  # reported alongside but not the H1 verdict

reported_metrics:
  - validated_factor_count_per_system
  - per_card_incremental_sharpe_with_ci
  - sealed_strategy_sharpe
  - sealed_strategy_max_drawdown
  - validation_to_sealed_degradation
  - acceptance_rate_trend
  - hypothesis_calibration
  - reuse_rate
  - safety_fail_count
  - tokens_total

multiple_testing_correction:
  family:               per_card_ci_tests
  method:               benjamini_hochberg
  false_discovery_rate: 0.10
  # FDR (not FWER) is appropriate here because each card is an
  # independent discovery candidate, not a confirmatory comparison.

The primary comparison is a single test; its p-value (equivalently, the CI lower bound) is the H1 verdict. Secondary comparisons are corrected for multiple testing using Holm-Bonferroni at family-wise error rate 0.05. Any comparison not listed in analysis_plan.yaml before sealed opens is reported as "post-hoc, exploratory" and explicitly cannot support H1.

Why this is the most important section Everything else in this proposal — the invariant suite, the redacted feedback, the Curator, the two-engine split — defends against specific reward-hacking and overfitting mechanisms. analysis_plan.yaml defends against the most common failure mode in ML research papers: choosing what to measure after seeing the data. Without pre-registration, even a perfectly-run experiment produces a verdict no honest reviewer should accept.

How LBG-Trader instantiates HL

Part II has now specified the methodology in full. This section steps back and audits it against the framing Weng's blog post crystallises under the name Heuristic Learning (HL): a learning loop whose updated object is software, not weights. The blog lists five properties HL ought to have. With every mechanism in this proposal now spelled out, we can read each property as a checkable promise and point to the exact section that delivers it. If a future reviewer asks "but does your project actually realise HL, or does it merely use the vocabulary?", §10.6 is the audit trail — and every reference below points backward, into specifications the reader has already seen.

The Weng-style dimension table, with our column

Weng's blog gives a two-column comparison (Deep RL vs HL). The third column below is LBG-Trader's concrete realisation. The point is not to show that HL is general — Weng's blog does that — but to show that the abstract HL slot is filled by a specific named file or function in this project.

The five HL properties, each mapped to a specific mechanism

Weng identifies five properties HL should have. For each, we name how LBG-Trader provides it, and where in this document the mechanism is specified. The intent is to make the implicit promise auditable.

1 · Explainability

HL claim. Code strategies can be translated into plain language; neural networks cannot.

LBG-Trader mechanism. Every accepted policy is the pair (strategy.yaml, indicators/*.py). The yaml is declarative and small; each indicator is a pure Python function with a mandatory docstring. The policy interpreter is fixed and human-readable. The final report (§17) includes a "strategy in one paragraph" rendering for every accepted artifact.

Verify at: §4.5 (formal H), §6.6 (skill artifacts include evidence), §17 (final report layout).

2 · Sample efficiency

HL claim. One good code edit jumps to a new policy; no slow gradient crawl through learning-rate space.

LBG-Trader mechanism. Each accepted trial is a structural jump in code space. The Discovery budget is 50 trials per run because each edit can change the feature set, not just a parameter — which the BO / grid baselines cannot do. Tier 4 of evaluation (§10.5) explicitly reports "Sharpe per million tokens" alongside Sharpe, so the efficiency claim is comparable to gradient-based baselines at equal compute.

Verify at: §5 (two-timescale), §10.5 Tier 4 (cost honesty).

3 · Regression-testable

HL claim. Old capabilities can become tests, replays, or golden cases that survive future changes.

LBG-Trader mechanism. Every accepted trial freezes a snapshot under artifacts/accepted/trial_NNNN/. The invariant suite re-runs on every candidate, so a future edit that breaks an old indicator's prefix-stability fails before it can be accepted. Failed directions are recorded in failed_directions.md and used to prune future Editor proposals. Curator re-validates skills against the latest trial set every cycle (§6.6).

Verify at: §6.5 (GitManager + SkillManager), §9 (invariants on every candidate), §10 Tier 3 (process metrics).

4 · Overfitting control

HL claim. Code heuristics can still overfit, but simplification, regression, and multi-seed checks form an engineering regularisation.

LBG-Trader mechanism. We stack four defences: (a) sealed evaluation (§7) — the single strongest one, opened once at the end; (b) the multi-objective gate's complexity penalty (§9), which rejects oversized edits; (c) the simplify edit type, explicitly available to the Editor; (d) re-discovery on fresh sealed windows (§13), the strategy-level analogue of multi-seed.

Verify at: §7, §9, §10.5 Tier 5 (pre-registration), §13 (re-discovery cadence).

5 · No catastrophic forgetting

HL claim. Old capabilities don't need to be remembered by the model; they live in rule sets and tests.

LBG-Trader mechanism. Git history is permanent: one commit per trial, one branch per Curator cycle, no rebase. accepted_rules.md survives every compression pass (Curator merges, never deletes without record). The skill store carries explicit evidence pointers. Any historical strategy artifact can be checked out and re-run by name; the LLM is not asked to remember any of this — the framework does.

Verify at: §6.6 (four memory layers), §10 (git discipline), §13 (lineage across re-discoveries).

Bonus · The HL property Weng's blog hints at but doesn't name

"There is a class of heuristics that, because maintenance was too expensive, was not previously worth writing — and that now might be worth owning long-term."

LBG-Trader mechanism. The whole skill artifact concept (§6.6) is designed precisely for this. A skill is not a passing optimisation; it is a maintained, evidence-bearing recipe that the framework re-validates every Curator cycle. The alpha-card export (§6.6) extends the same idea to signals, making the project's output a library of evaluated heuristics rather than a single point estimate of a strategy. This is the property that, if H1 holds, justifies the framework as a research product and not just a one-off experiment.

What this mapping does not promise

Two cautions. First, satisfying the HL property list does not by itself imply the strategy will generalise — that is what the sealed test is for, and what H1 / H2 / H3 will adjudicate. The HL properties are necessary infrastructure; they are not the verdict. Second, trading introduces failure modes that Weng's Atari-suite demonstrations do not stress (adversarial backtest surface, distribution shift, latent calendar priors in the LLM). The invariant suite (§9) and the redacted-feedback discipline (§7) exist precisely to defend HL's promised properties from being silently undermined by these trading-specific pressures. Without those defences, every property above would still be technically true while the resulting strategy would still be wrong.

III. Lifecycle — from sealed evaluation to deployment
§ 11

Four stages

This is the part of the proposal that bridges scientific evaluation and practical deployment. Each stage has a clean boundary, its own deliverable, and its own go/no-go decision. Stages are gated by humans, never auto-promoted.

1 Discovery

Sealed-evaluation LBG run

The Discovery engine runs an LBG loop on a chosen ticker and date range. Output: two artifacts in parallel — (1) a set of validated alpha cards (each a prefix-stable Python factor that survived the sealed test per §10.5 Tier 1), and (2) a frozen strategy.yaml + indicators/*.py that composes them — plus a sealed test verdict and the final report. This is the scientific core; it answers H1/H2/H3 for this ticker, this period, this protocol. The cards persist across re-discoveries (§13); the strategy is re-composed each time.

duration: hours to one day · cost: tens of dollars in tokens · deliverables: validated factor library + composed strategy

2 Forward validation

Out-of-sample backtest on data strictly after the sealed window

The frozen strategy is run against data the entire Discovery process never touched — strictly after the sealed window's last date. For the Stage 1 milestone (sealed = 2021-2024), Stage 2 begins at 2025-01-01 and uses whatever real history has accumulated since the strategy was frozen. This data is acquired after the Discovery artifact is sealed; it is never available to any Discovery run.

The deliverable is a backtest-to-forward gap report and a go/no-go signal for Stage 3. If the strategy's forward performance is substantially worse than its sealed expectation, it fails here and does not advance.

duration: minutes · cost: negligible · deliverable: go/no-go decision

3 Paper trading

Live data, simulated execution

The Execution engine runs the frozen strategy against real-time market data with simulated fills. No LLM in the loop — only policy_interpreter.py applying the deterministic rules. The deliverable is a live dashboard, a daily decision log, and a continuously updated backtest-to-paper gap monitor. This is "模拟实践" — the system is operating as if live, with all the operational mechanics, but with no real capital at risk.

duration: months · cost: data feed only · deliverable: live performance track record

4 Live capital

Real money, broker integration

Out of scope for this proposal but designed for: the Execution engine connects to a broker and trades small live capital. Risk monitoring, circuit breakers, reconciliation, audit — all of standard quant operational practice. This stage is optional and gated by Stage 3 performance.

duration: ongoing · cost: broker fees · deliverable: real returns

Two principles run through all four stages.

First, each stage's deliverable is consumable by the next stage and only the next stage. Stage 1 produces a frozen artifact; Stage 2 consumes that artifact and produces a go/no-go signal; Stage 3 consumes the artifact (only if Stage 2 was a go) and produces a live track record; Stage 4 consumes the live track record (only if Stage 3 was sustained). There is no skipping.

Second, only Stage 1 invokes the LLM. Stages 2, 3, and 4 are pure deterministic Python running the frozen artifact. This is what makes the two-timescale separation in §5 useful: live operation has zero LLM dependency, zero per-bar token cost, and zero risk of LLM availability outages affecting trading.

A day in the life of each stage

The stage table above is structural. This table is operational: what actually happens, who is responsible, and what files change on each kind of day. It is what an operator would put on the runbook wall.

§ 12

Two engines

The four-stage lifecycle reduces, architecturally, to two engines. This is the central engineering separation in the entire project.

Figure 4. Two engines, one shared artifact. The Discovery engine runs LBG loops to produce frozen strategy artifacts. The Execution engine reads frozen artifacts to forward-test, paper-trade, or live-trade. They never share runtime state. This separation is what allows scientific credibility and operational reliability to coexist.

This separation has consequences worth being explicit about:

  • The artifact is portable. A discovered strategy can be moved between machines, versioned in git, A/B compared, archived, or restored. It is just files.
  • Execution has no LLM dependency. An Anthropic outage during market hours does not stop trading. Paper trading and live trading depend only on a market data feed and (in Stage 4) a broker connection.
  • Discovery has no market-data-feed dependency. Discovery runs against historical parquet data; it does not care whether the broker is up.
  • Failure domains are isolated. Bugs in the LBG loop never corrupt live portfolios. Bugs in the Execution engine never invalidate sealed evaluation.

This is the standard ML system pattern — training pipeline and serving pipeline are separated — applied to LBG.

§ 13

Periodic re-discovery

A frozen strategy will eventually go stale. Markets change. Volatility regimes shift. New mechanisms become relevant; old ones decay. The question is not whether to refresh, but how, while preserving the scientific credibility of each refresh.

The naïve approach — let the agent keep learning from live data — destroys sealed evaluation immediately. Once the agent sees any data, that data can never serve as sealed for that agent again. The disciplined approach is periodic re-discovery on a fresh sealed window.

Figure 5. Periodic re-discovery preserves sealed-evaluation credibility by rotating the sealed window forward in time. Each re-discovery uses a fresh chunk of data that was not visible during the previous Discovery. The cost is patience: new sealed budget accumulates at the rate of real time passing.

Re-discovery triggers

What causes a re-discovery to fire is itself a design decision. Healthy options:

  • Calendar-based. Every quarter, every six months, every year. Predictable, easy to reason about, easy to budget.
  • Performance-based. When backtest-to-paper gap exceeds threshold (e.g., live Sharpe drops more than 0.3 below sealed expectation for 30+ days). Triggered by Stage 3 monitoring.
  • Risk-based. When live drawdown exceeds threshold. Pulls the strategy offline until re-discovery completes.
  • Data-availability-based. When enough new data has accumulated to support a meaningful new sealed window.

In practice the triggers compound: a regime change usually causes the performance trigger to fire before the calendar trigger would. The healthy default is calendar-based with performance-based early triggering.

Between re-discoveries: strategies are frozen

Between two re-discovery events, the strategy is frozen. The Execution engine simply runs policy_interpreter.py on whatever strategy.yaml + indicators/ are currently active. No edits. No LLM. This is what makes daily operation cheap, reliable, and reproducible.

This also means there is always exactly one active strategy artifact for a given universe, with clear lineage. If the Q1 strategy was 2026-Q1_spy_a and the Q4 re-discovery produced 2026-Q4_spy_a, the latter cleanly supersedes the former, and the Q1 artifact is archived for historical comparison and audit.

The factor library, by contrast, accumulates. Validated alpha cards from Q1 are not invalidated by Q4's re-discovery — they remain entries in the alpha-card library and may be re-composed into Q4's strategy if they still survive the Q4 sealed test. The Q4 Discovery run starts with the union (Q1 cards + new candidates) as its seed pool. Some Q1 cards will no longer validate on the new sealed window (they get marked deprecated with a dated note); some will continue to validate and be re-used; some new candidates will be added. Over multiple re-discoveries, the strategy artifact churns while the factor library trends upward in size and downward in dud-rate. This compounding is the durability claim in §2 made operational.

§ 14

Universe filter, not ticker selection

A tempting feature would be to let the agent choose which ticker to trade. Resist this temptation. Letting the agent select tickers from a large pool introduces a catastrophic multiple-comparison selection bias: if the agent silently runs Discovery on fifty candidate tickers and reports the best one, the reported sealed Sharpe is almost certainly luck, not skill.

The disciplined alternative: the agent learns a universe-applicable strategy, and a deterministic filter selects which tickers to trade. The Discovery run is anchored to a single ticker (or a single small universe), and the agent's strategy is forced to express its tradable scope through declarative criteria rather than naming specific tickers:

universe_filter in strategy.yaml 
universe_filter:
  min_market_cap_usd: 10_000_000_000
  min_avg_daily_volume: 1_000_000
  min_price: 10
  exclude_sectors: [financials]
  exclude_etf_categories: [leveraged, inverse]

At deployment time, this filter is applied to the broader market to produce the list of tickers on which the strategy operates. The agent has not selected those tickers — it has stated the conditions under which its strategy claims to apply.

This mirrors how alpha factors are designed in professional quant research: a factor is a universe-applicable function, not a ticker-specific oracle. We borrow the discipline.

Note on multi-ticker The MVP described in this proposal trains on a single ticker (SPY). True multi-ticker cross-sectional learning is a substantial scope extension that we treat as a future direction, not a current milestone. The universe_filter idea above sets up the abstraction so that the move to multi-ticker is additive rather than disruptive.
§ 15

Online HL — a different research problem

A natural question, raised during proposal review: why not let the agent learn continuously, in real time, from live trading outcomes? Strategy never frozen, always evolving. This is conceptually attractive — it would make LBG-Trader a fully continual learner, closer in spirit to online RL.

The honest answer: this is a different research problem, not an extension of this one. Several reasons.

Why online HL is hard

It dissolves sealed evaluation. Once the agent sees live data, that data can never serve as hold-out. The entire concept of "did this generalize?" loses meaning. The strongest evaluation available is rolling forward performance, which is noisy and lacks the inferential power of true hold-out.

The agent will chase noise. Every update is based on recent samples. Recent samples are noisy. Without a sealed test to anchor truth, the agent will systematically and persistently make changes that look locally good but are not real signal.

There is no clean stopping criterion. Token cost accumulates indefinitely. Memory grows indefinitely. The system never "finishes."

It is an open problem in the literature. Weng's own demonstrations were batch learning — running a task to convergence — not online. Online HL is on the research frontier and has no settled methodology.

The four-stage lifecycle with periodic re-discovery achieves most of what online HL promises (the strategy evolves with the market) while preserving most of what online HL gives up (each refresh has a credible sealed evaluation). It is the disciplined middle path that the quant industry actually uses.

We treat Online HL as an explicit future direction. If Stages 1–3 of this proposal succeed and the periodic re-discovery cadence proves too slow for some markets, a follow-up project could explore online HL with a redesigned evaluation framework — accepting weaker statistical inference in exchange for tighter loops. That is a different document.

§ 16

The human's role, by stage

The framework gives the human a different role at each stage. Across all stages, one principle holds: the human does not make trade-by-trade decisions, and does not intervene mid-run in the LLM loop. The human acts at the boundaries between stages, not within them.

Before Stage 1
Methodologist

Designs the protocol. Picks ticker, splits, DSL schema, edit types, invariants, gate thresholds, baselines, model selection, stop criteria. Once frozen, these are locked for the run. This is the most consequential human contribution to the entire project.

During Stage 1
Disciplined non-participant

Watches the trial monitor. Does not intervene. May abort on serious bug; may not adjust prompts, thresholds, or memory based on what they see. The only thing the human is allowed to do mid-run is stop the run entirely — never alter it. This discipline is what makes the sealed verdict credible.

After Stage 1
Scientist

Reads the final report. Decides the H1/H2/H3 verdict. Writes up findings. Decides whether to advance to Stage 2 (forward validation) or to revise the protocol and run a new Discovery on a different ticker / split / configuration.

Stage 2 → 3 gate
Reviewer

Reads the forward validation gap report. Decides go/no-go for paper trading. A strategy that fails here is archived, not patched — patching a sealed-tested strategy on its forward data leaks information back into the strategy.

During Stage 3
Operator and portfolio manager

Monitors the live paper-trading dashboard. Watches the backtest-to-paper gap. Decides when to halt a deteriorating strategy (degradation), when to trigger early re-discovery (regime shift), and when capital allocation should change across multiple active strategies. Does not override individual trades.

Stage 3 → 4 gate
Risk manager

Out of scope here, but documented for completeness: sets hard risk limits, configures circuit breakers, handles broker integration and reconciliation, manages compliance, holds the emergency stop. This role's standards are determined by external requirements (broker, jurisdiction, capital source), not by this proposal.

The pattern across stages is the same: the human acts at gates and on infrastructure, the system acts within stages. Where this pattern would normally fail in practice — humans cheating by quietly adjusting things mid-run — the protocol explicitly defends against by making such adjustments invalidate the verdict.

§ 18

Engineering plan

The plan covers Stage 1 (Discovery) in detail, plus the infrastructure shared with later stages. Stage 2/3 deployment work is described in §11 but timed only at a high level; it is downstream of Stage 1's verdict.

Week 1 · shared infrastructure

Data, backtest engine, splits, classical baselines

Fetch SPY 2010-2024 via yfinance, cross-check Stooq, store versioned parquet. Write features.py with fixed feature set. Implement 150-line vectorized backtest with cost model and lookahead invariant. Implement policy_interpreter.py (used by both engines). Implement buy-and-hold, SMA cross, random search, grid search, Bayesian optimization baselines. Exit criterion: buy-and-hold metrics match an independently computed reference within tolerance (indicative: annualized Sharpe in the 0.7–0.9 range depending on cost assumptions); random-search median Sharpe is near zero after costs; the Tier 0 sanity checks in §10.5 all pass.

Week 2 · DSL-editing LLM loop (ablation baseline)

Editor / Reflector loop with redacted validation

Implement the DSL schema. Write Editor and Reflector prompts. Implement structured proposal parsing, mechanical hypothesis-outcome calculation, append-only trials.jsonl. Run N=50 trials with DSL-only edits. This is the ablation baseline. Exit criterion: full trial log produced, sealed test deferred.

Week 3 · program-synthesis layer

Indicator authoring, AST invariants, sandbox

Add the add_indicator edit type. Implement the AST-based static invariant suite (no future shift, no negative indexing, whitelisted imports, pure function). Implement sandboxed execution with timeout and memory limit. Implement the dynamic lookahead test. This is the layer that makes the project LBG rather than LLM-BO. Exit criterion: an indicator function failing the lookahead invariant is correctly caught.

Week 4 · curator and full Discovery run

Shadow curator, full N=50 LBG-Trader run, final report

Implement Curator prompt and memory compression operations. Run full LBG-Trader for N=50 trials. Open sealed test once. Generate final report HTML. Compare against Week 2 ablation. Exit criterion: H1/H2/H3 verdict delivered.

Week 5+ · Stage 2 deployment

Forward validation infrastructure

Build the Execution engine. Implement lbg-trader validate CLI. Run frozen strategy against post-sealed data. Generate backtest-to-forward gap report. Decide whether to advance to Stage 3.

Stage 3 milestone

Paper trading deployment

Implement live data ingestion, daily decision loop, paper portfolio state, live dashboard. Build re-discovery scheduling. Run at least one re-discovery cycle to validate the lifecycle end-to-end.

§ 19

Risks

Arranged by what each risk would mean for the conclusion, not by probability.

Backtest overfitting

The central scientific risk. If the agent passes validation but fails sealed, the project demonstrates only the strength of overfitting under sealed protocol. Mitigations: DSL constraint, multi-objective gate, redacted validation, sealed write-once, block bootstrap CI. Final defense: report the failure honestly as H1 negative.

Reward hacking

The central engineering risk. A coding agent given Python execution will find lookahead, exploit cost-model edge cases, manipulate index alignment, or hide bad trades in exception handling. Mitigations: invariant suite, AST static analysis, sandbox execution, dynamic lookahead testing. The unconstrained-Python ablation is run specifically to measure how badly this happens when invariants are off.

Distribution shift in deployment

A strategy that passes Stage 1 sealed test may fail forward in Stage 2 or 3 because markets changed. This is not LBG's failure; it is a property of the market. Mitigations: Stage 2 forward validation as a hard gate, backtest-to-paper gap monitoring in Stage 3, performance-triggered re-discovery.

LBG claim overreach

The strongest temptation is to claim a positive H1 means "LBG works." The defensible claim is narrower: "LBG works on this DSL, this universe, this period, under this protocol." Mitigations: the DSL-only ablation is in the headline comparison; token cost is reported alongside Sharpe; we commit before the sealed test is opened to what each outcome would mean.

Heuristic system bloat

Without Curator, accepted_rules and indicators accumulate into a big ball of mud. Mitigations: complexity metric reported per trial; shadow Curator from day one; active Curator gated by validation re-check.

Dependence on the inner LLM

The framework is, internally, partly a neural network on the outer loop. Performance depends on the model used. A failure to reproduce with a different or weaker model would be a finding, not a fatal flaw — but it should be explicit. Mitigations: report model version and token cost; consider one ablation run with a weaker model.

Deployment risks (Stages 3–4)

Backtest-to-live gap may exceed acceptable bounds even after Stage 2 passes. Broker integration introduces operational complexity not addressed in this proposal. Mitigations: paper trading mandatory before live; performance-based circuit breakers; the deployment risk surface is documented in a separate operational design.

§ 20

Lock list

The following decisions are frozen for this milestone. Changing any of them mid-run invalidates the sealed test and resets the milestone.

Frozen decisions

  1. Repo named lbg-trader; paper title Sealed-HS: Persistent Heuristic Learning under Sealed Evaluation
  2. Single ticker SPY, daily bars, 2010-01-04 to 2024-12-31 for Stage 1 Discovery
  3. Three splits: train 2010-2018, validation 2019-2020, sealed 2021-2024; aliased split_A/B/C in agent context
  4. Agent action space: Python pure-function indicator authoring + DSL edits; eight discrete edit types
  5. Four LLM roles: Editor / Reflector / Curator / Translator; Curator is shadow mode in this milestone; Translator emits a dossier per accepted add_indicator
  6. Validation feedback to LLM is categorical only — never numbers, never curves
  7. Hypothesis outcome computed mechanically by Orchestrator, not by Reflector
  8. Invariants applied before any backtest: schema, AST static, prefix-stability dynamic, cost model, sandbox, no data snooping
  9. Per-trial validation gate uses multi-objective utility LCB at \(\alpha = 0.20\) plus Pareto improvement; does not require strict CI > 0 per trial
  10. Final H1 verdict uses moving block bootstrap of the paired difference (block_len 10, n_bootstrap 1000) against the pre-registered best baseline; CI95 lower bound > 0 is the strong criterion
  11. Effective per-side cost locked at 5.5 bps (5.0 base + 0.5 slippage proxy); applied uniformly across all systems including baselines
  12. Persistence via git: each trial is a commit; each Curator cycle is a branch
  13. Agent compute reported per role and as per-token efficiency, in baseline comparison table
  14. Sealed test opened exactly once; sealed_test_final.json is write-once
  15. Phase 0.5 baselines (random, grid, BO) run to completion before any LLM-driven run
  16. DSL-only LLM loop is an ablation, not a stage; runs in parallel with the full system
  17. Strategy is frozen between re-discoveries; never edited during Stages 2/3/4
  18. Re-discovery uses a fresh sealed window; old sealed windows are never reused
  19. For the SPY milestone, the framework fixes the universe to SPY; agent does not select tickers. The universe_filter mechanism in §14 applies only to future multi-asset milestones
  20. Stage 2 forward validation uses data strictly after 2024-12-31; this data is acquired after Stage 1 sealing and is never available to Discovery
  21. Online HL is out of scope; recorded as future direction in §15
  22. analysis_plan.yaml committed to git before any sealed test opens; primary and secondary comparisons are pre-registered there
  23. Secondary comparisons corrected for multiple testing using Holm-Bonferroni at family-wise error rate 0.05
  24. Skill artifacts conform to the §6.6 schema; the Curator's output is a typed object, not free-form prose
  25. Indicator functions must satisfy prefix-stability (§4.5); the dynamic invariant enforces this by perturbation testing
  26. Alpha cards exported on every accepted indicator-modifying trial (§6.6)
  27. Calendar labels (years, named events) appear only in human-facing final reports and in Orchestrator-internal logs; they are never present in agent prompt templates or in any file the ContextBuilder reads from
  28. HL object of learning is the Heuristic System: the union of indicators/*.py (Python factor functions), strategy.yaml, the explicit memory layers, and git lineage. The core artifact LBG produces within that system is the set of Python factor functions the agent has authored. Dossier and alpha card are translations / metadata views of those functions, not the deliverable
  29. H1 statistical unit is the surviving Python factor function, counted operationally via its alpha card: a function whose individual pathwise sealed incremental Sharpe has 95% block-bootstrap CI lower bound > 0 (block_len 10, n_bootstrap 1000). The pathwise interpretation — "without \(c\)" = policy at trial parent commit, "with \(c\)" = policy at trial commit — is the only operationalisation that covers every edit type without ad-hoc removal semantics. The H1 verdict is a count comparison across systems at equal compute budget; H1 strong requires LBG-Trader's count to strictly exceed the best baseline AND be at least \(\tau = 3\). Per-card validation is corrected for multiple testing using Benjamini-Hochberg at FDR 0.10
  30. The alpha-card schema (§6.6) is locked as a superset of the input dossier schema in knowledge/factors/dossiers/: declarative fields (factor_name, core_analysis, parameterization, combination_and_fusion) plus executable evidence (python_implementation_path, prefix_stability_passed, sealed_evidence, status). This makes round-trip translation Python ↔ dossier well-defined
  31. The validated-factor library is append-only and shared across re-discoveries. A surviving function (and its card) from run N enters the seed pool for run N+1; it is re-validated against the new sealed window and either retained, marked deprecated, or merged. Functions are never silently dropped
  32. External factor dossiers live under knowledge/factors/ (read-only, shared across runs) and are exposed to the Editor only via lbg.knowledge.search(). No dossier citation grants exemption from any invariant or from the sealed test
