§ 1

修订愿景 · 启发式系统作为学习对象

项目最初的描述是"用 LLM 提示工程跑 SPY 策略发现"。这套描述在 2026 年早春的方案里被改写过一次，又在 2026 年 5 月被改写过第二次。两次修订的方向都是把学习的对象搬到代码而不是参数上。

对照 Jiayi Weng 的 Heuristic Learning：HL 的学习对象不是神经网络权重，而是一个由代码、状态表征、反馈通道、记忆、更新机制构成的软件系统。每一次反馈不是去调一个数值参数，而是去修改这套软件中的某一处，加一段判断、写一个新函数、整理一份记忆。LBG-Trader 把这个范式映射到量化研究上的对应物如下：

Heuristic Learning 概念 LBG-Trader 对应物
policy / state representation indicators/*.py（智能体写的 Python 纯函数）+ strategy.yaml（声明式 DSL 把这些函数装配成策略）。这是核心学习对象。
feedback channels train 窗口的数值 metrics（智能体看得到）；validation 窗口的分类信号（智能体只看到 accept / reject_drawdown / reject_turnover / reject_complexity / reject_no_significant_improvement，永远看不到具体数字）。
records / memory 四层记忆：memory/trials.jsonl 事件流；memory/reflections.jsonl Reflector 解释；四份语义 markdown（accepted_rules / failed_directions / open_questions / do_not_repeat）；append-only memory/tried_factors.jsonl 跨 iteration 的因子尝试记录。
update mechanism 四个 LLM 角色组合：Editor 提交一条结构化编辑、Reflector 机械解释结果并更新记忆、Curator 每 10 次接受后压缩记忆、Translator 把每个被接受的 add_indicator 翻译成 JSON 形式的 dossier。每次更新一次 git commit。
HL 的产出物 不是某个单次 sealed Sharpe 数字，而是经过 sealed 验证的因子函数集合。每张 alpha card 是一条这样的函数加上它的 sealed 证据。Stage 1 跑下来增长几条 card，Stage 2 forward 再验证一次，这才是积累。

三个判断在第一阶段被反复确认

  1. 策略层 Sharpe 不是稳健的成功标志。v0–v7 八次 campaign 显示，单一 sealed 窗口的 ΔSharpe 可以因 baseline 选择翻转，v6 把 baseline 从 SMA-cross 换成 buyhold 后立刻出现"H1 weak True"，但这只是策略层的 supplementary 结果，不是修订后的主 H1。继续在策略层堆指标会回到 LLM-guided BO 的窠臼。
  2. 因子数量是更可积累的单位。主 H1 现在改为"sealed-validated alpha card 数量"。积累 才是 HL 在长程上想体现的，一条新的、有 sealed 证据的因子是可持续的产出，下一次 Discovery 还能在它上面继续修改。一个翻一次符号就消失的 ΔSharpe 不是。
  3. code 与 dossier 的双向流通是这次特别想做对的事。knowledge/factors/ 里 564 份 dossier 是项目最初的种子库，Editor 通过 substring 检索拿到 hint；反向，每被接受一个 add_indicator，Translator 就把 Python 源代码翻译回 dossier JSON 写进 alpha_cards/dossiers/。这样一次完整的 Discovery run 既消费 dossier 也产出 dossier，库会真的"长大"。这是 PROPOSAL §6.7 的"round-trip 桥梁"。
为什么是因子数量而非平均 ΔS 平均一组 ΔS_c 容易被单条极端的 card 拉动。一个框架如果"只发现了一条非常好的因子"，平均统计量看起来很漂亮，但实际上没有积累。计数则天然抗这个：每张 card 贡献 0 或 1，门槛是"sealed 95% CI 下界 > 0"。这与项目想表达的"HL 长出新东西"完全对应。

第一阶段的工程胜利是建好了 sealed 协议；第二阶段的科学挑战是真的让框架长出第一张可验证的 alpha card。

§ 2

主 H1 计量学 · pathwise incremental Sharpe

修订愿景需要一个能落到代码上的计量。PROPOSAL.html §10.5 Step 1 的数学描述是 leave-one-out：对每条接受的因子 \(c\)，对比包含与不包含 \(c\) 的策略在 sealed 窗口上的日收益差，做 moving block bootstrap，看 95% CI 下界是否大于 0。

严格的 leave-one-out 在 LBG-Trader 的 DSL 上无法干净定义：当 \(c\) 是 cross_above(fast, slow) 里的两条 SMA 之一时，"去掉一个 indicator"会把入场规则破坏掉，剩下的策略不再可执行。所以实现采用路径式解读：

\[ \text{"without } c\text{"} \;=\; \pi_{H_\text{at parent commit}}(D_\text{sealed}), \qquad \text{"with } c\text{"} \;=\; \pi_{H_\text{at trial commit}}(D_\text{sealed}) \] \[ \Delta r^{c}_t \;=\; r^{\text{with } c}_t \;-\; r^{\text{without } c}_t, \qquad \Delta S_c \;=\; \sqrt{252}\,\frac{\overline{\Delta r^{c}_t}}{\operatorname{std}(\Delta r^{c}_t)} \] 这条定义对全部八种 edit type 都生效，把"去掉 \(c\) 的策略"定义为这次 trial 之前的策略状态，把"带上 \(c\) 的策略"定义为这次 trial 接受之后的策略状态。Pathwise 沿着构造轨迹去掉 \(c\)，而不是从最终复合策略里抽象地去掉。

从 trial 到 sealed_summary 的实现路径

每张 alpha card 携带 source_trial 与 source_commit。后者是父 commit（在 trial 修改 strategy 之前的状态）。compute_per_card_sealed_validation 的步骤如下：

  1. 查找 subject 为 trial NNNN: 的 commit SHA（即子 commit，包含本次 trial 的修改）。
  2. 用 git show <parent>:strategy.yaml 与 git show <parent>:indicators/<fn>.py 把父状态物化到临时目录；同样物化子状态。
  3. 分别在 sealed 窗口（split_C，约 1006 个 bar）上跑 backtest，得到两组 paired daily returns。
  4. 对差值序列做 moving block bootstrap：block_len=10, n_bootstrap=1000, α=0.05。
  5. 把 {incremental_sharpe_point, incremental_sharpe_ci_lower, incremental_sharpe_ci_upper, n_bootstrap, block_len, alpha} 写回 card.evidence.sealed_summary。
  6. 找不到 trial commit 或者 sealed 窗口太短时，记一个 validation_error，但 sealed_summary 保留 None，这与"还没被验证"的语义一致，H1 计数器自然不会把它算进去。

消费端 · H1 verdict

\[ N^{\,\text{val}}_\text{LBG} \;=\; \#\bigl\{ c : \operatorname{lower bound}\bigl(\operatorname{CI}_{95}(\Delta S_c)\bigr) > 0 \bigr\} \] \[ \textbf{H1 strong} \iff N^{\,\text{val}}_\text{LBG} > \max_B N^{\,\text{val}}_B \;\text{ and }\; N^{\,\text{val}}_\text{LBG} \ge \tau \] \[ \textbf{H1 weak} \iff N^{\,\text{val}}_\text{LBG} \ge 1 \;\text{ and }\; N^{\,\text{val}}_\text{LBG} \ge N^{\,\text{val}}_{B^{*}} \] 基线注册在 analysis_plan.yaml：buy_and_hold、sixty_forty，初始 baseline_validated_counts: {}。\(\tau\) 预注册为 3。所有 baseline 在 sealed 上自然不产 card，因此 \(N^{\,\text{val}}_B = 0\)。

不变量 · 五层防御

  1. Pydantic schema · extra=forbid，DSL 不能塞未声明字段。
  2. AST 静态检查 · no_negative_indexing、no_future_shift、no_forward_fill_future、whitelisted_imports_only（仅 numpy / pandas / math）、pure_function（无全局变量、无副作用、无 I/O）。
  3. 受限沙箱 · 受控的 globals + SIGALRM 超时；指标代码即使绕过 AST 检查也跑不出文件系统。
  4. prefix_stability · 动态扰动 \(D_{>t}\) 检查 \(f(D)[t]\) 是否真的不变。这是最严的一层，单点扰动可以抓到任何 rolling、whole-series normalisation、forward-fill 引入的未来信息。
  5. protocol 不变量 · no_python_edit（智能体不得修改 backtest.py / policy_interpreter.py）、no_forbidden_file_access、no_data_snooping（年份、命名事件不得出现在任何会进 Editor prompt 的文件里）。

validation gate · 多目标，非"严格 CI > 0"

每个 trial 的 gate 是多目标决策，不要求严格的 CI 下界 > 0。组成项：最小成交次数、drawdown regression cap（验证窗最大回撤不能比当前增大 15% 以上）、turnover cap、complexity cap、单边 utility LCB（α 默认 0.20，permissive 配置下降到 0.40）、Pareto 改进、overfit gap cap。permissive 是给"探索阶段想真的产 card"用的；strict 留给最终发表。

sealed vault · 写一次

artifacts/sealed/sealed_test_final.json 是写一次。SealedVault 在任何二次写入时直接抛错，无法覆盖。Stage 2 起，scripts/campaign.py --seal-only-last 提供"只在最终一次 iteration 打开 sealed 窗口"的发表模式；默认每次 iteration seal 是 dev 模式，用来给 dashboard 实时看进度，但不能作为独立 H1 evidence（有效样本量是 1）。

§ 9

显著性硬化 · 这 11 个因子真的显著吗？

§8 给出 11 个因子，但留了一个尖锐的问题：跑了 15 次 campaign、上百次 trial，“被接受”不等于“显著”。一个搜索过程从噪声里挑出右尾，本身就会制造表观 alpha。本节记录为回答“怎么确保因子显著、而非搜索偶然”所做的一整套显著性硬化工作：三层多重校正、分辨力下限的明确承认、合成 null 标定，以及最终对每张卡片给出可辩护的经验 null p 值。结论先行：在本窗口本定义下 H1 = False，但这一次有经验 null 分布支撑，不再是“CI 恰好包含 0”的空话。

三层多重校正栈

校正回答的不是同一个问题，叠在一起才完整。三层都已实现并接入 sealed payload（lbg/verdict/，75 个单元测试）。

BH FDR
Benjamini-Hochberg，控 per-card FDR 于 0.10（PROPOSAL §20 第 32 条原本只写了规范、代码里没实现，本阶段补上）。对家族里所有卡片的单边 bootstrap p 值做 step-up，回答“逐张卡片的假阳率”。lbg/verdict/multiple_testing.py。
SPA
Hansen 2005 Superior Predictive Ability，家族级检验：“这一组卡片作为整体，至少有一张真显著吗”，并自动考虑候选间的相关结构。stationary bootstrap + SPA_l / SPA_c / SPA_u 三档。这是金融计量里专门回答“试了 N 个、最好那个还显著吗”的标准方法。lbg/verdict/spa.py。
DSR
Deflated Sharpe Ratio（Bailey & López de Prado 2014）：考虑“试了多少次”后，单张卡片 Sharpe > 0 的概率。输入 SR̂、偏度、峰度、样本长度、试验次数。纯 stdlib 实现（math.erf + Acklam 反正态），无 scipy 依赖。lbg/verdict/dsr.py。
分辨力下限 · ΔSR ≈ 0.30 年化 PROPOSAL §10.5 新增的注脚把这条写死了：T = 1006 个 sealed bar + block_len 10，Bailey-LdP 的 Sharpe 标准误公式给出 σ̂(SR) ≈ 0.5 年化，α=0.05、80% 功效下可靠分辨的最小增量约 ΔSR ≈ 0.30。低于此值的因子在本窗口上与零不可区分，它们“未被反驳”不应被读作“已被证实”。vol_regime_zscore 的 +0.249 正好坐在这条线下方，所以无论怎么校正，它的 CI 必然包含 0。

B3 不能做什么（写报告必须承认） 不测 pipeline 级 FDR（那需要 LLM 在环，是 Step 4 / B2 的事）；不验证 SPA / DSR 作为独立程序的校准；不解决 Stage 2 paper-trading 那个唯一干净的 OOS 问题；11 张卡片的家族对家族级校正功效本来就弱。还有一条不可由统计补救的根本约束：SPY 2021-2024 对 LLM 不是真 OOS，这段时期的因子文献在它训练数据里。真正干净的 OOS 只能由 Stage 2 在 >2024-12-31 数据上的 paper trading 提供。

完整回顾（含 codex / claude / mimo 三 provider 配额耗尽的 run 日志）见 docs/SIGNIFICANCE_HARDENING.md 与 docs/synthetic_null_results/。脚本：scripts/synthetic_null_calibration.py（pipeline 级）、scripts/per_card_null_distribution.py（B3 per-card）。

codex review 提出的 bug (c)（source_commit 指向被拒绝的 commit）当时只在代码层修复，无法在 v26 上重算，其 /tmp repo 已丢失。本次复查用 --provider codex_cli 重新跑了两次 3 轮 campaign（dev 多次开封一次、publication --seal-only-last 一次，共 60 trial），既验证了修复在真实运行中的行为，也意外得到一个把本节论点讲透的实例。这两次 run 不是新的 H1 证据，单窗口、effective n=1、家族级检验未拒绝；它们的价值是验证机制。

Stage 2 gate 条件

lbg.stage2.run_forward_validation 在 split_D 上跑 deterministic backtest，用一组宽松的 go/no-go 条件：

  1. 最小成交次数（避免无成交的 noisy "fit"）
  2. 最大回撤地板（明显爆仓直接拦）
  3. 最小 Sharpe（与 split_C 上的 sealed_summary 相对比，看 forward 是否塌缩）

Stage 2 通过即可进入 Stage 3 paper trading；不通过就是 backtest-to-live gap 的早期预警，触发 re-discovery（PROPOSAL §17）。Stage 4 live capital 默认不在本项目作用域。

re-discovery 协议

每次 re-discovery 必须使用一个新的、不重叠的 sealed 窗口（PROPOSAL §17）。旧 sealed 窗口被该次 Discovery 用过一次就永久作废，不允许复用。这是为什么 Stage 2 开局新增了 scripts/campaign.py --seal-only-last：development 模式（每轮 seal）只用于 dashboard 调试，发表 evidence 需要明示 publication 模式（一轮一 sealed）。下一步规划里会再加 walk-forward K 个不重叠子窗口，给主 H1 一个有效样本量 > 1 的版本。

所有 stage 不变量

  1. 策略 artifact 在 Stage 2/3/4 期间不修改。改策略的唯一方式是触发一次新的 Discovery（带新 sealed 窗口）。
  2. 因子库 (knowledge/factors/) + 已验证 card 库 (alpha_cards/) 在 stage 之间共享，但只读。
  3. cost 模型在所有 stage 一致：5.5 bps 每边（5.0 基础 + 0.5 滑点 proxy）。
  4. 任何 stage 的 bug fix 都视为重置当前 milestone，不能"修了 bug 重跑 Stage 2"假装这是同一次 evidence。
§ 11

路线图 · 从 11 个因子到 strict-H1 验证

v26 把因子库累积到了 11 个不同因子，但截至本报告：每张 card 在permissive gate 的成长期下被接受，sealed CI 严格 > 0 的还是 0 张（最强的 vol_regime_zscore 点估计 +0.27，CI lower 约 -0.09 仍跨过零）。下面四项按优先级排列，每项独立。

① strict 复检
用 strict gate 把 11 个因子各自重新评估个体 sealed CI。permissive gate 的 growth-phase Pareto 让 sharpe 微跌也能通过，因此 library 长得快但每个个体不一定贡献正信号。strict 复检：取 v26 期末的 strategy（带 11 因子），逐个对每个 indicator 做 pathwise sealed CI，挑 CI lower > 0 的子集组成"strict-validated subset"。这才是 PROPOSAL §10.5 意义下的 H1 比较对象。
② walk-forward sealed
K 个不重叠 sealed 子窗口。当前 sealed 是 2021-2024 单一窗口，主 H1 有效样本量是 1。把 split_C 切成 K=4 子窗口（2021、2022、2023、2024 各一年），对每张 alpha card 在 4 个子窗口上分别跑 pathwise CI，按多重比较的 Benjamini-Hochberg FDR=0.10 校正后再计数。这把 H1 strong 从一次单点 evidence 升级为 K 次独立 evidence。scripts/campaign.py --seal-only-last 是这条路径的 v1，walk-forward 是 v2。
③ 因子互补性度量
给 library 加 covariance / rank correlation 指标。当前 11 个因子里多个分类是 trend 类（ema_above_sma, donchian_position, aroon, kama_ratio）。如果它们之间高度相关，等效维度 < 11。给 library 中每对因子在 train 窗口算 rank correlation，可视化成热力图，下一次 Editor 给"低相关补充"信号，把 dashboard 的 library 表加一列"该因子和现有因子的最大相关系数"。
④ 类别覆盖度
主动诱导未触达类别。v26 期末仍有 4 类 seed template 从未产出 card：mean_reversion、volatility、drawdown、volume。在 Editor system prompt 里加一句"library 已有 X 类 N 个因子，建议探索：Y、Z 这两个还未触达的类别"，把覆盖度推到 7 类全占。

路径 ①② 的首次执行 · seal-only-last v1

codex review 复查顺带把 rung ② 提到的 --seal-only-last v1 路径执行了一次。用 --provider codex_cli 做了两次 3 轮 campaign：一次 dev 模式（每轮都开封 sealed 窗口），一次 publication 模式（仅末轮开封一次），都在 strict gate 下进行，接受的因子相同（vol_regime_zscore 与 body_to_range），差别只在 sealed 窗口的独立性。这是 strict gate、volatility_target 载体下的新 run，与上文 v26 permissive 库「strict-validated 0 张」并不矛盾：载体策略不同，分辨力下限未变。完整图表见 §9 B4。

不会做的事 · 排除项

  • 不在 Stage 2/3 期间编辑策略。改策略的唯一方法是新一轮 Discovery + 新 sealed 窗口。
  • 不打开 online 学习。PROPOSAL §15 已明示这是另一个研究问题。
  • 不引入多资产 universe。SPY 单资产锁定，universe_filter 留给未来里程碑。
  • 不绕开任何 invariant。library 里的 dossier 也走 prefix_stability、no_data_snooping、sandbox 全套校验，下一次 campaign 重新 ingest 时同样校验。
  • 不把 permissive 下产出的 library card 当作 H1 evidence。permissive 下的 card 是"探索阶段的候选"。要进入 H1 evidence 需要走 strict gate 复检 + walk-forward。

验收信号

下面三条同时出现，视为第二阶段最终成功（即"library accumulation → H1 evidence"路径走通）：

  1. strict gate 复检后 library 里至少 τ=3 个因子的个体 sealed CI lower > 0（PROPOSAL §10.5 的 H1 strong 标准）。
  2. 这 ≥ 3 个因子在 K=4 walk-forward 子窗口里至少 K' ≥ 2 个子窗口都给出正 CI（多窗口稳健性）。
  3. 这些 alpha card 对应的 Translator dossier 经人工抽样审阅，observation: 段都对应得上源代码事实。

三条中任一条不满足，本阶段 H1 视为 inconclusive（既不 strong 也不 weak），但 library 累积 + Python↔dossier round-trip 已经验证 LBG 工程流程的完整性。

§ 13

结语

第一阶段证明了可信的实验协议是可以建出来的；codexreview 分支证明了建好的协议里能稳定长出可记录的因子。15 次 campaign 从 0 alpha cards 推到 11 个不同因子（每个含 Python 源码 + JSON dossier + sealed CI 记录）。中间 7 次 gate 演化，每一次都为了堵住 LLM 找到的新捷径，这本身是 HL 范式的活体演示：被维护的软件系统每一轮都比上一轮聪明一点点。

诚实地说：到本报告定稿为止，主 H1（strict gate 下严格 sealed CI > 0 的 card 数）尚未在 11 个因子上系统复检。permissive 下点估计有正有负，CI lower 还跨着零。下一阶段要做的是 strict 复检 + walk-forward 多窗口，把"library accumulation"路径推到"H1 evidence"路径。这是科学验证；之前 codexreview 分支做完的是工程流程的搭建。两件事不能互相替代，但工程流程已经完整稳固，科学验证有清晰的起点。
