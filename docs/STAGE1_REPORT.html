TL;DR · 这是什么、谁在做什么

LBG-Trader 是一个把 LLM 当作策略改写者的发现框架：让 LLM 在严格的沙箱与 sealed-evaluation 协议里逐步提出 SPY 日频交易策略的小改动，由一个确定性的 Python 控制平面（Orchestrator）负责判别、记录、提交。所有 LLM 调用集中在三个明确的角色上，整个系统的可信度来自Orchestrator 自身从不调用 LLM。

核心方法学

三个相互独立但互锁的原则共同保证结果可信：

  • 结构上隔离 sealed window。split_C 的数据、指标、日期 agent 永远看不到，由 SealedVault 一次性写入。
  • 判定与解释分离。HypothesisScorer 机械判定 trial 是否符合 Editor 的预期；Reflector 只能解释 outcome、不能改写。schema 在结构上让覆写 outcome 不可能。
  • 多目标 gate 而非单 Sharpe。per-trial gate 同时考量交易数、回撤回归、换手、复杂度、效用 LCB、Pareto 改进、过拟合差距。任何一项越界就拒。

§ 2

架构全貌

Orchestrator 是一个确定性的 Python 控制平面。它调度每一次 LLM 调用、应用每一个 edit、跑每一个不变式、写每一个 artifact。Orchestrator 内部不包含任何 LLM 调用，它的确定性是整个实验可信度的基础。三个 LLM 角色坐在叶子节点，其它一切都是普通 Python。

图 1。 13 个确定性子模块环绕中央 3 个 LLM 角色。两侧的黄色虚线是结构层 redaction 屏障：agent 永远拿不到原始 OHLCV、日历年份或验证数字。Stage 2 与 Stage 3 复用同一套 backtest 引擎，全程无 LLM 介入。

§ 3

Discovery 循环的运转

一个 trial 等于一个 budget 步。每一步要么完整走完提案、构建、判别、反思、提交，要么干净地中止然后前进。整个循环短到能完整写出来：

算法 1 · 一个 trial 
for i in range(budget):
  trial_id = start_id + i                              # 顺序编号，中止也前进
  ctx       = ContextBuilder.editor_view(incumbent)
  proposal  = RoleRunner.editor(ctx, trial_id)         # LLM 调用 #1
  candidate = CandidateBuilder.apply(incumbent, proposal)

  if InvariantRunner.fail(candidate, df_train):       # AST + prefix_stability + sandbox
    MemoryManager.append_invariant_failure(...); continue

  train  = BacktestRunner.run(candidate, df_train)
  val    = BacktestRunner.run(candidate, df_val)

  gate   = ValidationGate.decide(incumbent_outcome, candidate_outcome)
  signal = ValidationGate.redact(gate)                 # 5 种类别化信号之一
  outcome = HypothesisScorer.compare(proposal, signal, train.sharpe_delta)

  refl   = RoleRunner.reflector(ctx, proposal,         # LLM 调用 #2
                                outcome, signal, train.metrics)

  MemoryManager.append_trial(record)                   # trials.jsonl
  MemoryManager.append_reflection(refl.record)         # reflections.jsonl
  MemoryManager.append_to_md(refl.record.updates)      # 4 份语义记忆 md
  GitManager.commit_trial(trial_id, edit_summary)

  if gate.accepted:
    incumbent, incumbent_outcome = candidate, candidate_outcome
  else:
    restore_working_tree(incumbent)

  if Curator.should_run(accepted_count):                # 每 10 个 accepted 触发
    Curator.run(cycle=...)                             # LLM 调用 #3，shadow 模式

# 循环结束
sealed_metrics = BacktestRunner.run(incumbent, df_sealed)
h1_verdict     = compute_h1_verdict(sealed.returns, df_sealed)
SealedVault.open_and_write({..., h1_verdict})         # 一次性写入
ReportBuilder.build()                                  # 最终 HTML

每个 trial 两次 LLM 调用（Editor + Reflector）。每 10 个 accepted trial 触发第三次（Curator）。在一次 20 trial、0 accepted 的运行中，整个循环消耗 40 次 LLM 调用。

§ 4

应对 agent 代码的分层防御

一个能编写 Python 并影响 backtest 的 LLM，从第一天起就是指标的对手，无论它是不是有意为之。不变式套件就是阻止它通过 reward hacking 写出虚假 Sharpe 的那道屏障。

图 3。 LLM 生成的 indicator 与回测之间的 5 层屏障。AST 静态检查捕获 agent 写下来的内容；sandbox 捕获通过了静态分析但在运行时违规的行为；prefix_stability 捕获 AST 永远看不到的语义层泄漏。Anthropic 20 trial 的运行里，12 / 20 个 trial 在到达 gate 之前就被这五层中的某一层拦下。

最关键的一项检查

五层中，prefix_stability 是为其它四层存在赋予意义的那一项。PROPOSAL §4.5 的形式化表述：

\[ f\!\left(D_{1:T}\right)\!\bigl[t\bigr] \;=\; f\!\left(D_{1:t}\right)\!\bigl[t\bigr] \qquad \forall\, t \in \{1, \ldots, T\} \] 对任意 indicator f，它在时刻 t 用全序列计算的值，必须等于它仅用截止到 t 的前缀计算的值。这比 AST 扫描 shift(-1) 严格得多：能捕获归一化、百分位等任何让 D>t 信息进入 f(D)[t] 的路径。

实施方式：随机采样 30 个 t，用 U(0.5, 1.5) 随机缩放替换 df.iloc[t+1:]（OHL 同步缩放以保持 high≥close≥low 的内在约束），重算 indicator，将头部 [0..t] 与未扰动基准比对。任何超过 atol=1e-12 的偏差视为泄漏。两个在实际运行中捕获到的 leaky LLM-authored indicator：

Indicator泄漏原因
whole_series_zscore (s - s.mean()) / s.std()。t=500 处的 mean 与 std 取决于所有未来行。AST 看不见这种泄漏（无 shift、无 iloc、无 fill）。prefix_stability 在第一次扰动就抓住：扰动 D>500 时，t≤500 的每一个值都跟着变。
normalize_to_global_max close / close.max()。结构问题一致，更直观。扰动后第一个差异位置：0。

两者都是 LLM Editor 在试运行中无诱导地生成的，都在任何回测之前就被拒。这就是这一层在工作。

一个诚实的局限 prefix_stability 采样无法证明不存在 lookahead，只能证伪。在 n_samples=30 时，若泄漏恰好只出现在 3000 个 t 中的某一个，约 99% 的运行会漏过。生产运行采样更激进，并由 Curator 记录每一次假阴性作为加大采样的证据。目前默认值对我们 DSL 内的日频 indicator 足够，但不能替代形式化证明。
§ 5

验证 gate

per-trial gate 是整个系统中最容易在不知不觉中与 H1 verdict 标准产生偏差的部分。它不是 H1 verdict。它有意设计得更宽松，避免 Discovery 循环被饿死，但又足够严格，让验证窗口上的偶然 accept 不会污染搜索。

lbg/gate/decision.py · decide() 
def decide(incumbent, candidate, cfg):
  if candidate.train.num_trades < cfg.min_trades:        return Reject("too_few_trades")
  if candidate.val.max_drawdown < incumbent.val.max_drawdown * 1.15:
                                                          return Reject("drawdown_regression")
  if candidate.val.turnover > cfg.max_turnover:           return Reject("turnover_too_high")
  if candidate.complexity - incumbent.complexity > cfg.max_delta:
                                                          return Reject("complexity_increase")

  u_cand = utility_lcb_sharpe(candidate.val.returns, α=0.20)
  u_inc  = utility_lcb_sharpe(incumbent.val.returns,  α=0.20)
  if u_cand > u_inc + cfg.eps:                            return Accept("utility_improvement")

  if pareto_dominates(candidate, incumbent, cfg.eps):     return Accept("pareto_improvement")

  if candidate.train.sharpe - candidate.val.sharpe > cfg.max_gap:
                                                          return Reject("overfit_gap")
  return Reject("no_meaningful_improvement")

为什么是单侧 utility LCB at α = 0.20

Lo (2002) 在 iid 日收益假设下给出的 Sharpe 估计量渐近标准误：

\[ \widehat{\mathrm{SE}}(\hat S) \;\approx\; \sqrt{\frac{1 + \tfrac{1}{2}\hat S^{2}}{n}} \cdot \sqrt{252} \] n 是验证窗口长度（split_B 约 505 个交易日）。Ŝ 是年化点估计。单侧下界用 α=0.20 对应 z0.80 ≈ 0.842。比 95% CI 宽，这是有意的：避免在 500 bar 的窗口上把每一个诚实的小改进都拒掉。

gate 比较的是候选 LCB与现任 LCB，而非点估计。候选 LCB 必须比现任 LCB 至少高出 EPS = 0.005。当两个候选的实现收益完全相同时，LCB 也相同，gate 就 fall through 到 Pareto 检查：仍可能因为复杂度、回撤或换手的改进被接受。

LLM 看到的 5 类类别化信号

gate 内部进行细致数值推理，但对 LLM 暴露的只有 5 种字符串之一：

对外信号内部理由映射
acceptedaccept_utility_improvement、accept_pareto_improvement
rejected_drawdown_regressionval MDD 超过现任 × 1.15
rejected_turnoverval 换手超出上限（默认 10 / 年）
rejected_complexityΔcomplexity 超过 MAX_DELTA（默认 3.0）
rejected_no_significant_improvementtoo_few_trades、overfit_gap、no_meaningful_improvement 共用此桶

把三个内部理由折叠到 rejected_no_significant_improvement 是有意为之。LLM 不需要区分 "我交易太少" 与 "我在 train 上过拟合"：两者都表示 "你的 edit 没有让策略前进"，正确的回应也都是 "试一种不同形态的 edit"。在 agent context 中区分它们会引诱 reward hacking，针对其中更容易触发的那个写作弊。

complexity 完整公式

五项之和，所有权重在 §20 锁定列表中冻结：

\[ \mathrm{Complexity}(H) \;=\; \lambda_1 |A_k| + \lambda_2 |\text{filters}| + \lambda_3 |\text{params}| + \lambda_4 \cdot \mathrm{LOC} + \lambda_5 \cdot \#\text{branches} \] 冻结权重：λ1=1.0（每个 indicator），λ2=0.5（每个 filter），λ3=0.1（每个 param），λ4=0.005（所有 indicator 文件累计的有效 LOC），λ5=0.05（If/While/For/Try 等 AST 控制流节点）。LOC 与 branch 在不同的 indicator 文件之间累计，两个 spec 共用一个 fn 不重复计数。

添加一个 50 行、3 个分支节点的 ATR 实现，会让 complexity 增加 1.0 + 0.005·50 + 0.05·3 = 1.4。MAX_DELTA = 3.0 意味着一个 trial 大致可以做两次这样的添加，第三次必须等 Curator 的 simplify 把存量复杂度先压下来。

§ 6

封存窗口与 H1 verdict

整个架构最重要的一条不变量是：agent 永远看不到 split_C。看不到数据、看不到指标、也看不到 split 边界的日历日期。Orchestrator 在 Discovery 循环的最末刻打开它一次，把 verdict 写入一次性 vault，由人类阅读。

图 4。 三个 split 在数据流中以 split_A / split_B / split_C 的别名出现，agent 永远看不到日历年份。坐标轴上的年份只是给人类读者参考。封存只在循环末尾打开一次。

H1 检验

最终判别是对 LBG-Trader 与最强 pre-registered baseline 之间 sealed Sharpe 的配对差做 moving block bootstrap 置信区间：

\[ \Delta\hat{S} \;=\; \hat{S}_{\text{LBG}} - \hat{S}_{B^{*}} \quad\text{with}\quad \mathrm{CI}_{95\%}(\Delta\hat{S}) \;=\; \bigl[\hat{q}_{2.5\%},\, \hat{q}_{97.5\%}\bigr] \] 百分位 q̂ 在 1000 次 bootstrap 重采样上取得。每次重采样从配对日收益序列里有放回地抽 ⌈n / block_len⌉ 个长度为 10 的重叠 block，重新计算两侧 Sharpe。B* 取两个 pre-registered baseline（buy-and-hold、sixty-forty）在 split_C 上点 Sharpe 较高者。

强判据是 CI.lower > 0；弱判据是 ΔŜ > 0。两者都报告，但 verdict 取决于强判据。

为什么用 block bootstrap

SPY 日收益存在非可忽略的自相关，波动率层面尤其明显。iid bootstrap（按日单独重采样）会抹平这种结构，进而高估 Sharpe 估计的精度。长度为 10 的 moving block 保留了短期自相关，又能在 1000 次重采样下给出稳定的 95% CI。

§ 7

反 sycophancy 的防御

如果直接问 LLM Reflector "这个 trial 是否得到了确认"，它倾向于答 "是"，特别是 system prompt 流露出在意进度的时候。我们的防御不是劝它别这样做，而是结构上不给它这个机会：我们从不问它那个问题。

"Memory 记录的是发生了什么。Reflector 解释，Orchestrator 裁决。"

HypothesisScorer.compare 这一段是机械的

Editor 的 proposal 含有两个枚举化的预测：

  • expected_train_signal ∈ {strong_improvement, mild_improvement, neutral, mild_regression, strong_regression}
  • expected_validation_signal ∈ {accept, reject}

gate 结束后，Orchestrator 计算 delta_sharpe_train = candidate.train.sharpe − incumbent.train.sharpe，用固定阈值 (±0.05, ±0.30) 分到同样的五个桶里。Reflector 被告知结果，不被询问结果。

train 桶val 是否吻合HypothesisOutcome
吻合吻合confirmed
不吻合不吻合disconfirmed
恰有一项吻合partially_confirmed

Reflector 的任务是窄小的：给定 outcome，机械地解释策略机制中是什么驱动了这个结果。system prompt 禁止它重述 outcome、禁止它评判 hypothesis、要求它对四份语义记忆文档给出 bullet 形态的更新。ReflectorOutputPayload 不包含 hypothesis_outcome 字段，schema 本身就让覆写机械结果在结构上不可能。

三层 redaction

L1
结构层。PastTrialSummary dataclass 不含 validation_sharpe / validation_max_drawdown / validation_turnover 字段。Editor 看不到 val 指标，因为承载 trial 历史的数据结构里根本没有这些字段。测试 test_past_trial_summary_omits_validation_metrics 在每次 CI 都验证这个不变量。
L2
文本层 · 发送方向。每个组装好的 prompt 在 messages.create 触发前都过 assert_redacted。匹配模式包括 [1990, 2050] 之间的四位数字年份、ISO 日期、35 个具名市场事件（如 covid、gfc、lehman、brexit、9/11）。任何命中都在请求发出网络之前抛 RedactionError。
L3
文本层 · 接收方向。同一个扫描器再过一遍 LLM 的原始响应。如果模型在 reflection 里幻觉了 "在 2020 的回撤之后..."，我们立刻报错，而非把一条泄漏 bullet 写进 accepted_rules.md。整个 trial 中止，下一次 Editor turn 看不到这条记录。

Reflector 真实积累的内容

即便在 0 个 accepted trial 的情况下，Reflector 也产出真实的、机械的、有证据支撑的 bullet。来自 MIMO run 的 failed_directions.md：

"在没有重构 entry/exit 规则的前提下，单独把 sizing 切到 volatility_target 会导致仓位频繁缩放、交易激增，整体并无净改善。"

"把慢线 SMA 从 50 拉宽到 100（fast 保持 20）能减少交易数，但同时把 exit 延后到了让 Sharpe 变差、val 端触发 drawdown_regression 的程度；这条慢线作为过滤器太钝。"

这些是 Reflector 在 trial 之后给出的、对 gate 拒绝原因的机械解释。它点名了机制（仓位频繁缩放、过滤器太钝），而不只是症状。三个 trial 之后，系统已经积累了一张非平凡的失败模式地图，下一个 Editor turn 会读到它。

失败的形态

两次运行交叉验证之后有三个共同模式：

  1. 两个 provider 独立发现了同一个最佳改动。change_sizing_mode → volatility_target 在 Anthropic trial 1 与 MIMO trial 0 都给出了 train Sharpe 0.722（比 baseline 高 0.029），逐位一致。这是 Orchestrator 确定性主张在 provider 切换后仍然成立的最强证据，也是 LBG 思想的一个小确证：好 edit 是可发现的。
  2. 每个真实的 train 改进都让 val 变得更差。vol-target sizing：val Sharpe 0.933 → 0.876。SMA 周期变宽：val Sharpe 0.933 → 0.223。val 窗口恰好对 baseline 极为友好，任何动作都付出代价。这正是一个反过拟合 gate 必须捕获的现象。
  3. 接受率 = 0 / 24。这不是设计意图，是数据使然。min_trades=20 加上小验证窗口上 1.15× 的 MDD 阈值，让 gate 不留情。LLM 的单步 edit 无法解决 "这个 baseline 在它自己的 DSL 里已经接近局部最优" 这一根本问题。这就是负向结果。

§ 9

这意味着什么，下一步做什么

对 H1 verdict 的诚实解读令人不舒服：LBG 框架在 SMA 20/50 起点上、20 trial 预算下，没有产出一个能胜过 buy-and-hold 的策略。这是结论，不是实现失败。原因按重要性排序有三：

1 · 数据
sealed 窗口本身很难。split_C 横跨 SPY 一段多 regime 的时段，既包含一次主要回撤也包含一次有力反弹。SMA cross 在 regime 切换中必然被反复砍。buy-and-hold 在 sealed 上的 Sharpe 0.861 反映了 long-only 持仓在那个时段拿到的强顺风，而 SMA cross 按定义会错过部分上涨。
2 · DSL
动作空间太窄。单步 parameter_change / add_filter / change_sizing_mode 无法把一个 SMA cross 改造为根本不同的策略形态。框架找到的最强改动（vol-target sizing）让 train Sharpe 移动 0.029。gate 不可能接受这么薄的候选，即使接受了，val 窗口也会惩罚任何偏离 baseline 的动作。DSL 需要组合式edit，或者 Editor 需要规划跨多个 trial 的策略序列。
3 · 预算
20 trial 太少。PROPOSAL §10 提出过 ~50 trial 的工作预算。在我们观察到的 0 接受率（两个 provider 合计 24 trial 都没有 accept）下，即使 50 trial 也无济于事：Editor 没有在学组合，只是在采样局部 edit。下一个实验不是 "更大 budget"，而是 "Editor 的先验更好"，可能通过更丰富的 skill artifact、多步规划，或者结构上更大的 DSL 实现。

§ 10

升级后的回炉重跑

§ 9 给出的下一步建议被全部实现，并且在原来"单次 Discovery + 一次 sealed"之外多加了一层 campaign——多次 Discovery 共享 semantic memory 与 alpha cards。本节记录两轮升级（六项框架改造 + 两项跟进修复）和两次新的实证 campaign（严格 gate 与 permissive gate 各三轮 iteration）。结论：框架的机械问题（noop add_indicator、parser abort、缺失因子先验、单次 Discovery 失败即终止）全部消除；但在 SMA(20/50) 起点上 H1 仍然为 False。这次是个更彻底的 False。

六项框架改造 · 各自解决什么问题

改造机制解决的 § 9 病灶
step 1 · 因子库注入 knowledge/factors/ 564 份 dossier 通过 ContextBuilder 进入 Editor 的 prompt——从当前 strategy 的 indicator 名 + 最近 trial 的拒绝信号派生检索词（波动率／回撤／趋势强度／均值回归 等中文关键词），dossier 文本里 [1990, 2050] 年份替换为 <YEAR> 以通过 redaction 守卫。 § 9 建议的"内置 indicator 模板"。Editor 现在能在 hypothesis 里显式援引 ADX、AmihudIlliq、Chandelier、LSMA、RSI、ATR-trail、vol_ratio 等已发表因子，而不是凭空造一个 indicator。
A · LLM 单调用 micro-retry RoleRunner.editor 在响应触发 redaction / 缺 YAML 代码块 / schema parse error 时，最多再发起 2 次自纠正调用（共 3 次）。redaction 失败时丢弃脏 assistant 回合避免把违禁 token 引回上下文；其他失败时多轮重发，AgentComputeRecord 新增 retry_attempts 与 retry_reasons 字段记账。 § 7 报告里 MIMO 出现 12 次 parser abort。该改造让"输出格式失败"不再消耗 trial 预算。本次 Anthropic 上的两次 campaign 共 30 trial 实际 retry 次数为 0——但 safety net 已就位。
step 2 · alpha cards 导出 accepted 且 edit_type=add_indicator 时 Orchestrator 写 alpha_cards/trial_NNNN.yaml + 追加 alpha_cards/index.jsonl，schema 是 dossier 的超集，含 train 指标、validation_signal、空白的 sealed_summary 槽位（待 H1 verdict 填充）以及可选的 dossier_link 指回种子库。Pydantic extra="forbid"。 PROPOSAL §6.6 新增的 round-trip bridge——把 "dossier ↔ Python ↔ alpha card" 三态绑定成一个可数对象。H1 计数（PROPOSAL §4）从"整体 paired ΔSharpe"改为"sealed CI 下界 > 0 的 card 数"。
step 3 · 拒绝 noop add_indicator Strategy.unwired_indicators() 返回未被 entry / exit / 任何 filter 引用的 indicator 名。AddIndicatorPayload 新增可选 attach: Filter | None——一次性把新 indicator 接入 filter。CandidateBuilder 检测到 unwired 状态直接抛 CandidateBuildError("unwired ...")，在 backtest 之前就拒掉。 § 7 报告里 Anthropic 5/8 的 trial 是 noop add_indicator。新 schema 让这种 trial 在结构上不可能发生：Editor 必须同时给出指标 + 接线，否则 builder 报错。本次两次 campaign 共 30 trial，noop 比例 0/30。

proposed_edit.change 在 EditProposal schema 里是 dict。getattr(dict, attr) 总是返回 fallback——所以从第一天起，所有从这里读 name / fn / params 的代码都默默拿到 None。受影响的不只是 A+B 的 indicator_fn 记录：

新 baseline · 用现有 DSL 表达 buy-and-hold

原 SMA(20/50) baseline 在 val 窗口上 Sharpe 0.93——结构性偶然，任何 entry filter 都把这个 baseline 拉下来。在那个起点上，add_indicator 在 Pareto 上无路可走，Editor 反复退回 sizing trick。把起点换成 buy-and-hold（always-long），filter 的作用从"过滤 entry 事件"变成"在 risk-off 期间退出"——一个理论上能减回撤而不伤 Sharpe 的方向。

在不改 schema 的前提下用现有 CrossRule DSL 编码 buy-and-hold：

baselines/buyhold/indicators/step_in.py     · [0, 1, 1, 1, ...]
baselines/buyhold/indicators/zero_baseline.py · 常量 0
baselines/buyhold/strategy.yaml
    entry: cross_above(step_in, zero_baseline)  → bar 1 触发一次
    exit:  cross_below(step_in, zero_baseline)  → 永不触发
    sizing: fixed_fraction 1.0

step_in 一次性跳变创造唯一一次 entry 事件；exit 永远不触发，所以仓位从 bar 2 持续到 sealed 窗口末尾。两个 indicator 都是 pure pandas 函数，prefix-stable trivially（输出只依赖 row index、不依赖任何数据值）。scripts/campaign.py 加 --baseline {sma_cross, buyhold} flag。
